# RB-02 回滚与升级失败演练

## 原则

1. **先止血再定位**：回滚不需要解释，解释放事后；
2. 镜像用不可变 tag（`sha-xxxx`），不用 `latest`；
3. 回滚不碰数据，只切镜像；数据问题走 `restore.sh`。

## 实测

`make rollback TAG=0.3.0` → **12 秒**完成：校验本地镜像存在 → 改 `APP_VERSION` → 重建 api/ingest/web → 轮询 `/healthz` 直到报出目标版本。

拒绝「半截回滚」：目标 tag 的镜像不在本地时直接退出，不动线上。

## 步骤

```bash
make rollback TAG=v0.1.0    # 切 tag → 重建 → 健康检查
make verify                 # 确认可用
```

## 验收

- 版本号在 `/healthz` 里可见且与 TAG 一致；
- 看板恢复出数；
- 数据集未回退（除非显式 restore）。

## 升级失败演练（P9-5，2026-11-21）

### 怎么造一个"坏版本"

桩镜像：`/healthz` 永远 503，容器起得来但永远不 healthy。

```dockerfile
FROM python:3.12-slim
RUN mkdir -p /app && printf '%s\n' \
  'import http.server' \
  'class H(http.server.BaseHTTPRequestHandler):' \
  '    def do_GET(self):' \
  '        self.send_response(503); self.end_headers(); self.wfile.write(b"bad build")' \
  'http.server.HTTPServer(("0.0.0.0", 8000), H).serve_forever()' > /app/bad.py
CMD ["python", "/app/bad.py"]
```

```bash
# 打桩镜像并补齐另外两个组件的 tag（rollback.sh 会校验三者都存在）
podman build -t interroll-poc-api:0.3.2 -f <上面那个 Containerfile> .
docker tag interroll-poc-ingest:0.3.1 interroll-poc-ingest:0.3.2
docker tag interroll-poc-web:0.3.1    interroll-poc-web:0.3.2
```

### 演练步骤与实测

| 步骤 | 动作 | 实测 |
|---|---|---|
| 1 | 记录 `telemetry` 行数 | 9,027,607 |
| 2 | `APP_VERSION=0.3.2` → `compose up -d api` | 容器起来，`/healthz` 返回 **503** |
| 3 | 等 compose 判定 `unhealthy` | **48 s**（`start_period 20s + interval 15s × retries 3`）|
| 4 | `bash deploy/scripts/rollback.sh 0.3.1` | **12 s** 回到 0.3.1，`/healthz` 报版本 |
| 5 | 再记录行数 | 9,052,015（期间数据照常入库，**未回退**）|

**端到端 60 秒 = 检测 48s + 回滚 12s。**
"30 秒回滚"指的是第 4 步（决定回滚之后）；如果要求端到端 30 秒，得把 healthcheck 调紧
（`interval 10s / retries 2 / start_period 10s` ≈ 30s 检测），或者由部署脚本主动探活而不是等 compose。

### 关键点

- 回滚只切 `APP_VERSION`、只重建应用容器，**不碰数据库**；
- `rollback.sh` 先校验目标 tag 的三个镜像都在本地，缺一个就退出，**不做半截回滚**；
- 升级失败期间 ingest 仍在写库，所以"数据没动"是指**没丢数据**，不是"行数不变"。
