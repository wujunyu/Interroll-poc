# RB-03 排障

## 先看三处

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 看板无数据 | `make ps` 容器状态 | db 没 healthy，ingest 起不来 |
| 数据断一段 | 补传水位线（`/healthz`） | 断网、spool 满、幂等冲突 |
| 曲线卡顿 | 浏览器 Performance | 窗口太长，没走聚合/LTTB |
| 时间不对 | 容器时区、设备时钟 | 时钟偏移（PoC 只记录不校正） |

## 日志（JSON，一行一条）

```bash
docker logs --tail 50 interroll-poc-ingest-1 | jq -r '"\\(.ts) \\(.level) \\(.msg)"'
docker logs interroll-poc-api-1 2>&1 | grep '"level": "error"'
```

字段：`ts / level / svc / msg`，必要时带 `zone / drive / trace_id / rows / spool / detail`。

- 全量上限：每个容器 `10m × 3`（compose 里 `x-logging`），不会写满边缘机磁盘；
- 崩溃栈：进程启用了 `faulthandler`，段错误/死锁会把栈打到 stderr，`docker logs` 里能看到。

## 事件表（不是日志流水，是"发生了什么"）

```sql
select ts, kind, severity, detail from events order by ts desc limit 20;
```

当前会记：`ingest_start` / `ingest_stop` / `db_recovered` / `spool_replayed`。
一天几十条，适合做审计与时间线；`make diag` 会导出最近 200 条为 `events.ndjson`。

## 退出码怎么读

```bash
docker ps -a --filter name=interroll-poc --format '{{.Names}}\t{{.Status}}'
```

| 退出码 | 含义 | 首查 |
|---|---|---|
| 0 | 正常退出 | —— |
| 1 | 应用异常 | 日志里的 traceback |
| **137** | SIGKILL（常见 **OOM**） | `docker inspect --format '{{.State.OOMKilled}}'` |
| 143 | SIGTERM（`docker stop`） | 正常停栈；ingest 会先 flush 再退 |

## 压缩会拿锁（实操踩过）

`compress_chunk()` 会对该 chunk 取强锁。我们在运行中的库上压缩最旧的 chunk，观察到：

- `select max(ts) from telemetry`（不带时间谓词）会扫**所有 chunk**，与压缩互锁，队列里堆了 3 个查询；
- 压缩本身从「几秒」变成「等了 5 分钟」才拿到锁。

结论：

1. **别在业务高峰压缩**，交给 `add_compression_policy` 在冷 chunk 上做；
2. 水位查询别写全表 `max(ts)`，加 `where ts > now() - interval '1 day'` 让 chunk 裁剪生效；
3. 压缩只压「不会再写」的 chunk（我们的策略是 7 天前）。


## 前端断线会自动重连（2026-11-21 补）

`useLive` 之前只把 `connected=false`，连接断了就永远停在那里。现在：

- `onclose` 里做**指数退避 + 抖动**（500ms 起，上限 30s，±50% 随机）；
- 重连成功后 `attempt` 归零；
- 服务端每帧都发**全量快照**，所以重连后的第一帧就能补齐状态，不需要额外拉历史。

实测：`docker restart api` 后，浏览器 9 秒内恢复 10fps（20 帧/2s）。


## WebSocket 生命周期（2026-11-21 补全）

| 事件 | 服务端行为 | 可观测字段 |
|---|---|---|
| 连接建立 | `clients += 1`，写 `ws connected` 日志 | `/healthz` → `ws.clients` / `ws.accepted` |
| 正常发送 | 每 100ms 一条全量快照（约 4.8 KB） | `ws.fps` |
| **客户端读不动** | `send` 超过 `WS_SEND_TIMEOUT`（默认 2s）→ `close(1013)` | `ws.timeouts` 递增 |
| 客户端断开 | 捕获 `WebSocketDisconnect`，协程退出 | `clients` 递减 + `ws closed` 日志 |
| 服务重启 | 连接断开，前端指数退避重连（500ms 起，上限 30s） | 前端头部显示「WS 重连中…」 |

**为什么用超时而不是协议 ping**：我们 10fps 本来就在持续发数据，发不出去就是最强的存活信号；
再叠一层 ping/pong 只会增加状态。半开连接最迟在 `WS_SEND_TIMEOUT` 内被发现。

**验证**：

```bash
python scripts/test_ws_timeout_unit.py    # 假连接直接验证超时分支（3 秒）
python scripts/test_ws_timeout.py         # 真实网络慢客户端（需更久填满缓冲）
```


## WAL 与线程看门狗（2026-11-21 补）

**ingest 的数据落盘顺序**：`on_message` 先追加 WAL（内存→page cache）→ flush 时 `fsync` →
入库 → 推进 `wal.commit` 游标。崩溃后从游标重放，重复由主键挡掉。

| healthz 字段 | 含义 | 异常判据 |
|---|---|---|
| `wal_pending_bytes` | 未提交的 WAL 字节数 | 持续增长 = 库写不进去 |
| `replay_thread_alive` | 回放线程是否活着 | `false` = 线程死了（看门狗会重启）|
| `replay_tick_age_s` | 回放心跳距今秒数 | > 10s = 线程卡住 |
| `frame_age_s` | 最后一条 MQTT 消息距今 | > 60s = 上游断了 |

**为什么要有看门狗**：Python 的 daemon 线程异常退出不会影响进程，也不会有人通知你。
主循环每 0.2 秒检查 `_replay_thread.is_alive()`，死了就重启并写 `replay thread died` 日志。

**实测崩溃恢复**：

```
基线 0 → 发 500 条 → kill -9（此时库里 315）→ 重启 → 500 ✅
日志：crash tail recovered
```

注意边界：**进程崩溃不丢（page cache 还在），断电仍可能丢最后 ≤1 秒**
（WAL 的 fsync 发生在 flush 时，不是每条追加时）。
