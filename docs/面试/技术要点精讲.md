## 0. 先背这条主线

### 0.1 一条链

```
36 台驱动 @10Hz
   │  MQTT QoS1（line/{zone}/drive/{drive}）
   ▼
mosquitto（边缘 Broker，1884）
   │  持久会话 clean_session=false + client_id=ingest-1
   ▼
ingest：每条追加 WAL → 攒 200 行 / 1s → executemany + ON CONFLICT
   │                          └─ 失败：WAL 就是兜底，游标不推进
   ▼
TimescaleDB：telemetry（hypertable）+ telemetry_1m（连续聚合）
   │                          └─ 保留 7d/90d、压缩、pg_stat_statements
   ├── api：REST 查历史（≤5m 原始 / >5m 聚合）+ WS 推实时（10fps）
   │        └─ 实时帧直接来自 MQTT，不回查库
   └── forwarder（center profile）：按水位把边缘行推到中心库（PK 多 site_id）
```

### 0.2 三段责任边界（面试先讲这个）

| 段               | 断的是谁          | 谁兜底             | 本项目实现                                                  | 做不到的                |
| --------------- | ------------- | --------------- | ------------------------------------------------------ | ------------------- |
| 设备 → 边缘 Broker  | 现场网络          | **设备自己**        | 模拟器 `--offline-at/--offline-for` + ndjson spool + 限速补发 | 真设备要改固件；平台只能定契约     |
| Broker → ingest | ingest 重启/OOM | **Broker 持久会话** | `clean_session=false` + 固定 `client_id`；QoS1 排队         | Broker 自己崩且没持久化，仍会丢 |
| ingest → DB     | 库挂/慢/进程崩      | **ingest**      | 预写日志 `wal_append/wal_replay`，先落盘再入库                    | 断电仍可能丢最后 ≤1s        |

一句话：**“不丢”不是一个数字，是每一段各自的兜底 + 端到端幂等键。** 面试时先问“哪一段断”，再答“谁兜”。

### 0.3 三个必须带口径的数字

| 口径 | 算式 | 结果 | 备注 |
|---|---|---|---|
| 每拍 | 6 区 × 6 驱动 | 36 点 | 同一采样时刻 |
| 每秒 | 36 × 10Hz | 360 点/秒 | 实测边缘库严格 360/s |
| 每分钟 | 360 × 60 | 21,600 点 | = 36 驱动 × 600 点/驱动/分钟 |
| 每天 | 21,600 × 1,440 | 约 3,110 万点 | 当前库实测约 160B/行（含索引），约 5 GB/天量级 |
| 断网 1 小时 | 360 × 3,600 × 约 147–180B | 约 190–230 MB | 需求文档估 190MB，按 180B/行约 230MB；不是实测 |

**RPO 要分三种“死法”说：**

| 死法 | 丢多少 | 为什么 |
|---|---|---|
| `docker stop`（SIGTERM） | 0 | `_on_sigterm` → `KeyboardInterrupt` → `flush()`（`code/ingest/main.py:306-312, 398-399`） |
| `kill -9`（进程崩） | 0 | 数据已写进 page cache 的 WAL，重启从 `wal.commit` 回放（C-PIPE-009 实测 500/500） |
| 断电/内核崩 | 最后 ≤1s | `fsync` 在 flush 时做（`wal_sync()`，`code/ingest/main.py:94-96`），不是每条追加时做 |

### 0.4 五组最容易混的概念

| 容易混 | 正确说法 |
|---|---|
| QoS1/2 = 端到端不丢 | QoS 是**每一跳、每个会话内**的保证；PUBACK 只到 Broker，不等于落库。端到端还要应用层幂等 + 设备缓存到业务确认 |
| “先落盘” = 每条 fsync | 代码是“每条追加到 WAL 文件（进 page cache），flush 时 fsync 整批”。进程崩不丢，断电丢最后 ≤1s |
| 水位 = 行数 | 水位是 `max(ts)`，表达“补到哪”；行数会因重复/乱序不等于水位 |
| hypertable 一定更快 | 小数据量下普通表 + 时间索引可能更快（2M 行实测 8.4ms vs 11.3ms）；hypertable 的价值在淘汰、压缩、索引规模 |
| 压缩 = 保留 | 压缩是 chunk 级列存，保留是 drop chunk；两者阈值都设 7 天时，压缩窗口≈0（见 §12） |

## 1. 架构与拓扑

> 导图原句：
> - 边缘 5 容器：mqtt / ingest / db / api / web
> - 同源入口 :5174（nginx 反代 /api /ws）
> - 边缘 → 中心：forwarder 按水位推送
> - 中心库主键多一列 site_id

### 1.1 五个容器，各自只做一件事

| 容器       | 镜像                                  | 宿主端口           | 只做一件事              | 挂了会怎样              | 怎么发现                                           |
| -------- | ----------------------------------- | -------------- | ------------------ | ------------------ | ---------------------------------------------- |
| `mqtt`   | `eclipse-mosquitto:2`               | 1884→1883      | 转发 + 持久会话          | 边缘断流，设备/ingest 各自兜 | healthcheck `mosquitto_sub $SYS/#`；`/api/mqtt` |
| `db`     | `timescale/timescaledb:latest-pg17` | 5433→5432      | 原始点 + 1m 聚合        | 全线停（采集进 WAL）       | `pg_isready`；`/healthz.db`                     |
| `ingest` | 自建，224MB                            | 无（health 8081） | 订阅 + 批量 + WAL + 幂等 | 数据积压，WAL 涨         | `/healthz` 的 `wal_pending_bytes`、`lag_seconds` |
| `api`    | 自建，310MB                            | 8001→8000      | REST + WS 10fps    | 只影响展示，不影响落库        | `/healthz`、WS 断线提示                             |
| `web`    | 自建 nginx，96MB                       | 5174→80        | 静态资源 + 反代          | 只影响展示              | 浏览器；`/healthz` 反代                              |

两个**可选** profile，不算边缘五件套：

| 服务 | profile | 作用 | 为什么单独 |
|---|---|---|---|
| `simulator` | `demo` | 造数 360 点/秒 | 现场演示才起，不污染交付栈 |
| `center-db` + `forwarder` | `center` | 多机演练的中心库 + 水位转发 | `make up` 默认不起，`make center` 才起 |

**精确说法**：`make up` 起 **5 个**容器；`docs/README.md` 说“6 个容器”是把可选的 forwarder 算进去了。面试时说“边缘 5 个，中心演练再加 1 个 forwarder + 1 个中心库”，最稳。

### 1.2 同源入口 :5174

`code/web/nginx.conf` 四件事：

| location | 行为 | 为什么 |
|---|---|---|
| `/` | `try_files $uri /index.html` | SPA 前端路由，刷新不 404 |
| `/api/` | 反代 `http://api:8000` | 前端只用相对路径，无 CORS |
| `/healthz` | 反代 api | 页面头部直接显示版本/连接状态 |
| `/ws/` | 反代 + `Upgrade`/`Connection` 头 + `proxy_read_timeout 3600s` | WebSocket 必须显式升级，长连接不能被 60s 默认超时切断 |

**最值钱的一行**：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
set $api_upstream http://api:8000;
proxy_pass $api_upstream$request_uri;
```

nginx 默认**只在启动时解析一次** upstream 域名。`docker compose up -d api` 重建容器后 IP 变了，nginx 还拿旧 IP → **502**。用变量 + `resolver` 强制每 10s 重新解析，才修掉。这是“容器编排下反代”的经典坑，面试可以主动讲。

开发模式另一套：`code/web/vite.config.ts` 把 `/api`、`/healthz`、`/ws` 代理到 `127.0.0.1:8090`（宿主端口，避开 8080/8088）。生产走 nginx，开发走 Vite，两条路径不要混。

### 1.3 边缘 → 中心：为什么不用 MQTT bridge

ADR-0007 的对比，面试可以直接背：

| 维度 | A. MQTT bridge | B. 应用层转发（本项目） |
|---|---|---|
| 断链 6 小时 | 只能靠 broker 队列（`max_queued_messages` 默认几千条就丢） | 边缘库落盘，**断多久都不丢** |
| 重放/补偿 | 难（要重放 broker 日志） | 天然（改水位即可） |
| 只传聚合 | 难 | 易（转发时只发 1m 聚合） |
| 幂等 | 依赖 broker | 主键 `(site_id, zone_id, drive_id, ts, seq)` |
| 复杂度 | 低 | 中（多一个常驻进程 + 水位逻辑） |

**一句结论**：工业现场 WAN 断几小时是常态，broker 队列扛不住，只有落地库才可靠。

但有两个“说得到、做不到”的地方，必须知道：

1. **ADR-0002 说“中心只收聚合结果”，forwarder 代码实际推的是原始行。** `code/forwarder/main.py:31-44` 的 `SELECT_EDGE` 选的是 `telemetry` 全列，`INSERT_CENTER` 也是全列；没有查 `telemetry_1m`。所以中心库 24M 行 / 5GB，不是“864MB/天”的聚合口径。ADR-0002 的“事后回看”也写着“待补：52GB → 864MB/天 是否成立”。**面试口径**：“PoC 先把‘不丢’做扎实，转发的是原始行；聚合回传是产品化下一步，ADR-0002 的决策还没落地。”
2. **`bundle.sh` 不含 forwarder / simulator / `init-center.sql`。** 离线包只能起边缘五件套；要演练中心侧，得在源码仓库里 `make center`。`rollback.sh` 也只重建 api/ingest/web，center profile 下 forwarder 会留在旧版本。

### 1.4 中心库为什么多一列 site_id

```sql
-- 边缘 deploy/db/init.sql
PRIMARY KEY (zone_id, drive_id, ts, seq)

-- 中心 deploy/db/init-center.sql
PRIMARY KEY (site_id, zone_id, drive_id, ts, seq)
```

- 多站点汇聚时，两个站点的 `Z1/D01` 是同名设备；没有 `site_id` 会撞主键。
- `site_id` 放最左，符合“先按站点裁剪”的查询习惯。
- 中心 chunk 是 **1 day**，边缘是 **1 hour**：边缘要频繁 drop 7 天前的数据，chunk 小一点淘汰更细；中心保留更久、写入更集中，chunk 大一点减少 chunk 数。
- 中心多一个 `forwarded_at timestamptz default now()`，便于排查“什么时候到的”，但不参与主键。

**追问：为什么不在边缘库也加 site_id？**
边缘机只服务一个站点，加了是冗余；站点身份由 forwarder 的 `SITE_ID` 在跨机时注入。这样边缘 schema 保持最小，中心才承担多站点语义。

### 1.5 这一节的讲法（30 秒）

> “边缘是五个容器：mqtt、ingest、db、api、web。采集和展示解耦——看板挂了不影响落库。对外只有一个 5174，nginx 同源反代 /api 和 /ws，避免 CORS，也避免前端写两个地址。跨机不走 MQTT bridge，走应用层 store-and-forward：边缘库是唯一事实源，forwarder 按水位推，幂等键在中心多一个 site_id。代价是多一个常驻进程和一套水位逻辑，但 WAN 断几小时也不丢。”

**高频追问**

| 问                     | 答                                                     |
| --------------------- | ----------------------------------------------------- |
| 为什么不用 K8s？            | 一台工控机，控制面纯亏；集成商不会维护 etcd（ADR-0001）。                   |

## 2. MQTT

> 导图原句：
> - QoS 实测：0 丢 151 / 1 全到 / 2 少其一
> - 有效 QoS = min(发布, 订阅)
> - 持久会话 clean_session=false + 固定 client_id
> - 重连退避：paho 默认 1→120s，压到 1–2s
> - 抖动两种：offset（每台固定）/ full（每次重抽）
> - $SYS 指标：connected / maximum / dropped / 1min 速率
> - Broker 选型：mosquitto 2.7MB vs EMQX 245MB
> - EMQX 强项：连接限速、每客户端指标、集群
> - 许可：mosquitto EPL-2.0，EMQX BUSL-1.1

### 2.1 QoS 0/1/2 的真实差别

实验条件（`code/simulator/qos_lab.py`，mosquitto 2.0，2026-11-20）：
300 条 @100 条/秒，订阅端在第 1.0 秒断线 1.5 秒，`clean_session=false`。

| #   | pub | sub | 有效  | 发送  | 唯一收到 | 丢失      | 重复  |
| --- | --- | --- | --- | --- | ---- | ------- | --- |
| A   | 0   | 0   | 0   | 300 | 149  | **151** | 0   |
| B   | 1   | 1   | 1   | 300 | 300  | 0       | 0   |
| C   | 2   | 2   | 2   | 300 | 299  | **1**   | 0   |
| D   | 2   | 0   | 0   | 300 | 149  | **151** | 0   |

三个结论：

1. **有效 QoS = min(pub, sub)**：A vs D 完全一样，发布端用 QoS2 也被订阅端 QoS0 拉平。Broker 的 `max_qos`、ACL 也可能再降，但这条语义不变。
2. **QoS1 在 1.5 秒断线里靠 Broker 排队补回 150 条**，一条不丢；重复为 0 是因为链路干净，真实弱网重传会出现重复。
3. **QoS2 仍丢 1 条**（seq=99，正好落在断线时刻）。它在四段握手中间：PUBLISH → PUBREC → PUBREL → PUBCOMP。QoS2 保证的是“会话内、每一跳不重复”，不是“业务端到端 exactly-once”。断线在途、Broker 崩、应用收到但没落库，都可能丢/重。

**所以数据面仍要应用层幂等**：`(zone_id, drive_id, ts, seq)` 主键 + `ON CONFLICT DO NOTHING`。这不是“多此一举”，是 QoS 语义的补丁。

### 2.2 持久会话：clean_session=false + 固定 client_id

`code/ingest/main.py:340-355`：

```python
cli = mqtt.Client(..., client_id="ingest-1", clean_session=False)
cli.subscribe("line/#", qos=1)
```

- `clean_session=false`：ingest 重启期间，Broker 保留订阅和 QoS1 队列；重连后补投。
- 固定 `client_id`：Broker 靠它找回会话。如果每次启动换 id，旧会话的排队消息就没人取了。
- 判断会话是否恢复：看 CONNACK 的 `session_present`。代码在 `on_connect` 里打日志（`:349-350`）。

**paho 2.x 的坑（C-MQTT-003）**：复用同一个 `Client` 对象、手动 `disconnect()` 后再 `reconnect()`，Broker 会记 `session taken over`，`on_connect` 不触发，排队的消息一条也收不到。第一次跑 QoS1 丢了 200 条就是这个原因。

正确做法（`qos_lab.py:63-77`）：**每次重连新建 `Client` 对象，但 `client_id` 不变**。

**要分清两种重连**：

| 场景 | 做法 | 会不会踩坑 |
|---|---|---|
| 手动 `disconnect()` → `reconnect()` | 复用同一 Client | 会，paho 2.x 的 session taken over |
| 网络断了，`loop_start()` 自动重连 | paho 内部复用同一 Client | 通常不会；ingest 走的是这条 |

所以 ingest 没有手写重连，只设了 `reconnect_delay_set(1, 2)`；QoS 实验台才需要“新建 Client”。面试别说成“所有重连都要新建 Client”。

### 2.3 重连退避：1→120s 压到 1–2s

paho 默认 `min_delay=1, max_delay=120`：断网后 1s、2s、4s…… 最多 120s 才重试一次。现场要求“恢复后 10 秒内追平”，120s 的尾巴不能接受。

`code/ingest/main.py:347`、`code/api/main.py:125`、`code/simulator/main.py:55` 都改成 `reconnect_delay_set(min_delay=1, max_delay=2)`。

**实测（C-PIPE-003）**：断流 10 秒、补传限速 1200 条/秒，追平时间从 **21.7s → 10.6s**，唯一改动就是这三处退避。

**代价**：单客户端没问题；360 台设备都固定 1–2s，断网恢复时会形成重连风暴。所以设备侧要指数退避 + 抖动，ingest/api 这种“单客户端关键路径”才压到 1–2s。两者不是一个策略。

### 2.4 抖动：offset vs full

`code/simulator/fleet.py` 两种模式：

- **offset**（默认）：每台设备抽一个固定起点 `min_delay = 1 + uniform(0, jitter)`，之后按 2 倍翻倍，`max_delay = min_delay * 2`。设备之间错开，但同一台设备的节奏固定。
- **full**（AWS full jitter）：每次重试都 `random(0, min(cap, 1 * 2^attempt))`，`cap = max(jitter, 1) * 4`；代码里手动接管重连（`:48-79`），并加 0.2s 下限防空转。

实测（C-PIPE-004，360 台设备各一条连接，Broker 停 10 秒，1s 采样）：

| 模式 | jitter | 峰值重连 | 恢复时间 |
|---|---|---|---|
| offset | 0 s | **664 /s** | 1.3 s |
| offset | 3 s | 248 /s | 6.9 s |
| offset | 10 s | **44 /s** | 19.5 s |
| full | 3 s | 67 /s | 9.9 s |
| full | 10 s | 51 /s | 22.7 s |

**结论要精确**：

- 抖动不减少总重连负载，只是**把峰值换成时长**。
- 同样 jitter 上限下，full 的峰值不一定更低：jitter=3 时 67 vs 248（明显低），jitter=10 时 **51 vs 44（反而略高）**。导图写“full 峰值更低（67/51）”是把两组混在一起了，别概括成“full 一定更低”。
- 选 jitter 先定“能容忍多长的恢复窗口”：要 5 秒内齐，jitter=10 反而不合格。

另外两处抖动：启动相位 `--stagger`（每台 `uniform(0, stagger)` 秒后再连，`:44`）、发布相位（每台按自己的 `next_tick` 对齐，`:61-62`）。三处一起才叫“抖动”，只做重连退避不够。

### 2.5 $SYS 指标：三个一起看才有意义

| 指标 | 回答什么 | 注意 |
|---|---|---|
| `clients/connected` | 现在多少设备在线 | 断流期间应掉到 0 |
| `clients/maximum` | 开机以来峰值 | 重连风暴的直接证据 |
| `load/connections/1min` | 连接**速率** | 风暴的领先指标 |
| `publish/messages/dropped` | 队列满导致的丢弃 | 补传不限速时会涨 |
| 拒绝连接 | `max_connections` 挡掉的数量 | `$SYS` 没这项，要解析 Broker 日志 |

暴露位置：`code/api/main.py:243-251` 的 `/api/mqtt`；`deploy/scripts/diag.sh` 的 `mqtt-sys.txt`；`scripts/chaos_multi.py` 的 Sampler 只订 `clients/connected`。

**方法论局限（面试可以主动说）**：`chaos_multi.py` 算的是 `clients/connected` 的**净增量/秒**，不是 Broker 实际 accept 次数。如果设备重连后又快速掉线，净增量会低估风暴。更准的是 Broker 日志或 EMQX 的 `client.connected` 事件计数。PoC 用 `$SYS` 是因为 mosquitto 够用、无需额外组件。

### 2.6 Broker 选型：mosquitto vs EMQX

先纠正一个口径：导图的 **2.7MB vs 245MB 是内存占用（RSS），不是镜像体积**。

- 镜像体积（本机 `docker images`）：`eclipse-mosquitto:2` **42.4MB**，`emqx/emqx:5.8.4` **342MB**（未压缩）。
- 运行内存（2026-11-22 `docker stats --no-stream`）：本项目 mosquitto **6.68MiB**；宿主另一个 mosquitto **2.53MiB**；EMQX **183.5MiB**。
- 导图的 2.7/245 在仓库里找不到采样记录；按当前实测，**量级结论成立（约 30–70 倍），但具体数字要带采样时刻**。面试说“空闲 RSS 2–7MB vs 180MB 级”最稳。

| 维度 | mosquitto | EMQX |
|---|---|---|
| 内存 | 几 MB | 180MB 级 |
| 连接限速 | 无内建 | 有 |
| 每客户端指标 | 弱（`$SYS` 聚合） | 强（Dashboard/REST） |
| 集群 | 无原生集群 | 有（商业授权） |
| 许可 | EPL-2.0（弱 copyleft，按文件） | **5.8.4 开源版是 Apache-2.0；5.9+ 才统一 BSL-1.1**（单节点生产免费，集群/托管要商业授权） |

**许可这条导图写错了**：本项目 `deploy/compose/compose.emqx.yaml` 钉的是 `emqx/emqx:5.8.4`，开源版是 Apache-2.0，不是 BUSL-1.1。BUSL 从 5.9.0 起才成为统一许可；5.0–5.8.x 是企业版 BSL、开源版 Apache-2.0。面试若被问“EMQX 许可能不能用”，答：“我们钉的 5.8.4 开源版是 Apache-2.0；如果升级到 5.9+ 并要做集群，需要商业授权。”

**TimescaleDB 的许可也顺带说清**：核心是 Apache-2.0，但压缩、连续聚合、保留策略等 Community 功能走 **TSL**。TSL 允许自用、随增值产品分发，但不能拿 TimescaleDB 本身做托管 DBaaS。它不是 GPL/AGPL，不违反项目的“不引 GPL/AGPL”约束，但也不是 OSI 开源。这个区分在面试里很加分。

**为什么默认还是 mosquitto**：边缘机 2–4GB，180MB 的 Broker 是浪费；连接数 36–360，mosquitto 足够。EMQX 留给“要看每客户端指标/要做集群”的中心侧。

### 2.7 补传必须限速（这条比 QoS 更值钱）

C-PIPE-001 的实测：

| 做法 | 结果 |
|---|---|
| 断网 8 秒，恢复后 0.1 秒内全速喷 2880 条 | 落库 7134/7200，**丢 66 条** |
| 限速 400 条/秒 | **7200/7200** |

原因：Broker 逐客户端队列有上限（mosquitto 默认 1000 条），订阅端消费不过来就丢。**“恢复瞬间的洪水”比断网本身更危险。**

本项目的缓解：
- `code/simulator/main.py:104-107` 每 50 条按 `replay_rate` 补 sleep；
- `deploy/compose/mosquitto.conf` 把 `max_queued_messages` 提到 **10000**；
- `max_inflight_messages_set(500)` 放开客户端在途窗口（默认 20 会把 QoS1 吞吐压在几百条/秒）。

注意：`max_queued_messages 10000` 只是把水位抬高，不是消除风险；限速逻辑仍要保留。这是“配置 + 代码”双保险。

### 2.8 这一节的讲法（45 秒）

> “MQTT 这块我做了三组实验。第一，QoS 0/1/2 在订阅端断线 1.5 秒时的真实差别：QoS0 丢 151/300，QoS1 全到，QoS2 还丢 1 条——因为断线瞬间在四段握手中间。所以 QoS2 也不是端到端，数据面还得靠 `(zone, drive, ts, seq)` 幂等。第二，有效 QoS 是 min(pub, sub)，发布端用 QoS2、订阅端 QoS0 会被拉平。第三，补传必须限速：全速喷 2880 条丢 66 条，限速 400 条/秒就 7200/7200。另外 paho 2.x 有个坑：手动 reconnect 复用同一个 Client 会 session taken over，必须新建 Client、复用 client_id。”

**高频追问**

| 问 | 答 |
|---|---|
| QoS2 为什么还丢？ | 断线在四段握手中间，在途窗口没走完；QoS 是 hop-by-hop，不是端到端。 |
| 为什么 ingest 用 QoS1 不用 QoS2？ | QoS1 + 应用层幂等已经够；QoS2 四段握手更重，断线仍有在途窗口，收益不值。 |
| 为什么固定 client_id？ | Broker 靠它找回持久会话；换 id = 新会话，排队消息没人取。 |
| 重连退避压到 1–2s 会不会风暴？ | 单客户端关键路径可以；多设备必须指数 + 抖动，fleet.py 就是干这个的。 |
| `$SYS` 的峰值能证明风暴吗？ | 只能看净在线数峰值；要 accept 速率得看 Broker 日志或 EMQX 指标。 |
| mosquitto 2.7MB 是镜像大小吗？ | 不是，是 RSS；镜像是 42MB。EMQX 镜像 342MB、RSS 180MB 级。 |

### 2.9 QoS 怎么选：先问两个问题

QoS 不是“可靠性等级”，是**交付语义 + 代价**：

| QoS | 语义 | 谁在重传 | 代价 | 最常见的误解 |
|---|---|---|---|---|
| 0 | 最多一次（fire and forget） | 没人 | 延迟/开销最低 | “Broker 会帮我存”——默认不会给离线客户端排 QoS0 |
| 1 | 至少一次 | 发布端 / Broker 重传 | 可能重复 | “收到就落库了”——PUBACK 只到 Broker |
| 2 | 恰好一次（**会话内、每一跳**） | 四段握手 | 延迟/开销最高 | “端到端只处理一次”——应用崩了仍可能重复/丢 |

选型先问两个业务问题：

1. **这条消息丢了，业务能不能接受？**
   - 能 → QoS0。
2. **不能丢；那重复一条，业务能不能接受/去重？**
   - 能 → QoS1。
   - 不能（非幂等副作用，比如“累加计数”“阀门切换”“扣款”）→ QoS2；但 QoS2 仍不是端到端，业务侧还要幂等键/事务。
3. **需要历史、批量、断点续传？** → 不要用 MQTT QoS 解决，落库/HTTP/对象存储更合适。

具体场景：

| 场景 | 建议 | 为什么 |
|---|---|---|
| 10Hz 速度/温度遥测，看板看趋势 | QoS0 可接受；要逐点分析/计件用 QoS1 | 下一秒有新值，丢一个点曲线几乎看不出；要“每个点都对账”才必须不丢 |
| 告警/故障事件 | QoS1 + `event_id` 去重 | 丢一条告警比重复一条更严重；重复可由事件 id 挡掉 |
| 控制命令（启停/复位） | QoS1 + `command_id` + 设备幂等 | “启动”重复执行通常无害；“累加/切换”类命令必须幂等或 QoS2 |
| 计费/计量/不可重复动作 | QoS2 或 HTTP 事务 + idempotency key | MQTT QoS2 只保证会话内；真正的 exactly-once 要靠业务键去重 |
| 最新状态/设备影子 | QoS1 + retain | retain 只保留**最后一条**，不是历史队列；新订阅者立刻拿到当前值 |
| 历史补传/大批量 | 不要用 MQTT | 用 forwarder/水位/批量同步；MQTT 适合“实时消息”，不适合“搬历史” |

**为什么本项目选 QoS1，而不是 0 或 2**：

- 需求是“不丢不重”；QoS0 在 1.5 秒断线里丢 151/300，直接排除。
- QoS2 四段握手，断线瞬间仍丢 1 条，且延迟/吞吐更差；它换来的“会话内不重复”并不能替代业务幂等。
- QoS1 + 幂等键 `(zone, drive, ts, seq)` 能把“至少一次”变成“业务上的恰好一次”，成本更低。
- 一句话：**用应用层的幂等，换协议层的简单。**

### 2.10 “客户端/服务能恢复，数据就能恢复”吗？

**不能。** 这句话把三个“恢复”混成了一个：

| 恢复什么 | 靠什么 | QoS 管不管 |
|---|---|---|
| **连接**恢复 | TCP/MQTT reconnect | 不管 |
| **会话**恢复 | 固定 `client_id` + `clean_session=false`（3.1.1）/ `session_expiry_interval`（5.0） | QoS1/2 的离线排队依赖它 |
| **数据**恢复 | 发布端 outbox/spool + Broker 持久化 + 订阅端 WAL/幂等 + 应用层确认 | **QoS 不管** |

按故障类型拆开看：

| 故障 | QoS0 | QoS1 | QoS2 | 还需要什么 |
|---|---|---|---|---|
| 网络短暂断开，客户端自动重连 | 丢 | 持久会话下补投 | 同左 | 固定 client_id + `clean_session=false` |
| 订阅端进程重启 | 丢 | 队列补投（若会话持久） | 同左 | 同上；换 client_id 就没了 |
| Broker 重启 | 丢 | 取决于 `persistence` / autosave | 同左 | `persistence true` + 磁盘；mosquitto 默认 autosave 1800s，崩溃可能丢最后一段 |
| Broker 崩溃/断电 | 丢 | 可能丢最后一段 | 同左 | 更严格的持久化 + 上游补偿 |
| 订阅端收到后、处理前崩溃 | 丢 | 可能重复/丢 | 同左 | 应用层 ack/WAL/幂等；paho 在 `on_message` 返回后才回 PUBACK（QoS1）/ PUBREC（QoS2），回调里没落盘就崩，Broker 可能认为已送达 |
| 发布端发出后崩溃 | 丢 | 未收 PUBACK 且未本地持久化则丢 | 同左 | 发布端 outbox/spool |

**结论**：QoS 只保证“消息在**会话内、每一跳**怎么交付”，不保证“数据在故障后一定还在”。数据可恢复 = **持久化 + 确认 + 幂等**，三件套缺一不可：

1. **发布端持久化**：发之前先落 outbox/spool；收到 PUBACK 才删。本项目的模拟器断网时写 ndjson，但“在线时进程崩在 publish 途中”仍可能丢——真实设备要 outbox。
2. **Broker 持久化**：`persistence true` + 合理的 `max_queued_messages` / `max_queued_bytes` / 过期时间；否则离线太久或队列满，QoS1/2 照样丢。
3. **订阅端持久化 + 幂等**：先落 WAL 再入库；回调里没落盘就崩，Broker 认为已送达（paho 已在回调返回后回执）。本项目的 WAL + `(zone, drive, ts, seq)` 就是这一层。
4. **应用层确认**（可选但更强）：设备保留到收到业务 ACK，而不是 QoS 的 PUBACK；本项目模拟器是简化版，补发完就删缓存。

### 2.11 回到实验：QoS2 为什么还丢 1 条

**先明确：按 QoS2 的协议语义，这条消息本不应丢。** 丢的原因是客户端在重连时没有保留 QoS2 会话状态；这是 paho 的实现限制，不是 QoS2 的正常行为。

- 在**会话状态完整**（同一个 Client 对象，或客户端把状态持久化）时，QoS2 是“会话内不丢不重”的；只有客户端把接收状态丢了，才会出现 §2.12 的情况。
- 断线发生在四段握手中间（PUBLISH → PUBREC → PUBREL → PUBCOMP）；Broker 会从握手断点续传，但它只能续传“Packet ID”，不能续传“payload”——payload 在接收端的状态里。
- QoS2 的 exactly-once 是**每个会话、每一跳**的语义，不是“发布端到订阅端业务处理”的端到端持久化语义。
- QoS1 300/300 的前提是：**新建 Client + 同一个 `client_id` + `clean_session=false`**。如果 `clean_session=true`，Broker 会丢掉离线队列，QoS1 也补不回来。
- 有效 QoS = `min(pub, sub)`；发布端 QoS2、订阅端 QoS0，等于 QoS0。
- PUBACK 只到 Broker，不等于落库；所以“QoS1 + 主键幂等”才是数据面的完整方案。

**一句话记忆**：

| QoS | 记忆 |
|---|---|
| 0 | 发出去就不管，丢了不知道 |
| 1 | 至少送到，可能送两次；要能去重 |
| 2 | 会话内不丢不重；前提是双方会话状态都在；不是端到端持久化 |
| 要“恢复后数据还在” | 发布端存 + Broker 存 + 订阅端存 + 业务幂等；QoS 只是其中一层 |

> 延伸阅读：同目录的 [EMQX《MQTT QoS 0、1、2 解析：快速入门指南》](EMQX-MQTT-QoS-0-1-2-解析.md)（网页剪藏，含 11 张原理图；讲了 QoS1 重复、QoS2 四段握手与 Packet ID 释放）。

### 2.12 为什么 QoS2 实验丢了 1 条：PUBREC 与 PUBREL 之间的窗口

**结论先行：按 QoS2 的协议语义，这条消息不应该丢；这次丢的是 paho 的客户端状态，属于实现缺陷，不是 QoS2 的正常行为。**

**复跑数据**（2026-11-22，容器 mosquitto 2.1.4，paho 2.2.0；同 `qos_lab.py`，300 条 @100/s，第 1.0 秒断 1.5 秒）：

```
QoS2: sent 300, received 299, unique 299, duplicates 0, lost 1,
      missing_preview [99], session_restored [false, true]
QoS1: sent 300, received 300, unique 300, duplicates 0, lost 0,
      session_restored [false, true]
```

把 `--offline-at` 改成 1.5 / 2.0，缺失的 seq 会变成 149 / 199，有时又是 0 丢失。**不是固定丢第 99 条，而是“断线瞬间正在 PUBREC→PUBREL 之间”的那一条**。

**抓包级证据**（给 paho 打开 debug logger）：

断线前：

```
Received PUBLISH (m100)        # 订阅端收到 seq=99（mid 100）
Sending PUBREC (Mid: 100)      # 订阅端回了 PUBREC
Sending DISCONNECT             # 但还没等到 PUBREL 就断开
```

重连后：

```
Received CONNACK (1, 0)        # session_present=1：Broker 的会话还在
Received PUBREL (Mid: 100)     # Broker 从 PUBREL 继续，不是重发 PUBLISH
Sending PUBCOMP (Mid: 100)     # 新 Client 没有 mid=100 的记录，直接回 PUBCOMP
Received PUBLISH (m101) ...    # 没有 m100 的 PUBLISH，on_message 永远不会为 seq=99 触发
```

**根因在 paho 2.2.0 的 QoS2 接收端**（`_handle_publish` / `_handle_pubrel`）：

1. 收到 PUBLISH：**先回 PUBREC**，把消息存进 `_in_messages[mid]`，状态设为 `wait_for_pubrel`；**此时还不调用 `on_message`**。
2. 收到 PUBREL：如果 `mid` 在 `_in_messages` 里，取出、调用 `on_message`、回 PUBCOMP。
3. 收到 PUBREL 但 `mid` **不在** `_in_messages` 里（新建 Client 的状态是空的）：**不调用 `on_message`**，直接回 PUBCOMP。源码注释原话：

> “Choose to acknowledge this message (thus losing a message) but avoid hanging. See #284.”

所以：**Broker 没丢，它按协议从 PUBREL 续传；是客户端的“半边状态”丢了。** `clean_session=false` 只是让 Broker 保留会话，**不会**让 paho 把 `_in_messages` 落盘；换一个 `Client` 对象，客户端状态就清零。

**断线落在哪一步，决定会不会丢**：

| 断线时机 | Broker 的状态 | 重连后 | 结果 |
|---|---|---|---|
| PUBLISH 还没发到订阅端 | 消息在会话队列 | 重发 PUBLISH | 不丢 |
| PUBLISH 已发、没收到 PUBREC | 等 PUBREC | 重发 PUBLISH | 不丢 |
| **收到 PUBREC、没收到 PUBREL** | **等 PUBCOMP** | **重发 PUBREL** | **新 Client 无记录 → 丢 1 条** |
| PUBREL 已处理、on_message 已跑 | 等 PUBCOMP 或已完成 | 回 PUBCOMP | 不丢（应用已收到） |

同一时刻最多只有一条消息处在这个窗口里，所以**最多丢 1 条**；断线没踩中窗口就是 0。

**QoS1 为什么不丢**：paho 收到 PUBLISH 就调用 `on_message`，再回 PUBACK。PUBACK 丢了，Broker 重发 PUBLISH，新 Client 收到后照样交付；重复由业务键挡掉。QoS1 没有“应用交付前必须先有接收端状态”的窗口。

**这也解释了 paho 2.x 的两个坑是同一枚硬币**：

- 复用同一 `Client` 手动 `reconnect()` → `session taken over`，QoS1 也收不到；
- 换成“新建 Client + 同 client_id” → QoS1 好了（300/300），但 QoS2 的 `_in_messages` 没了，边界消息丢 1。

**修法**：

1. 保持同一个 `Client` 对象跨重连（paho 的内存状态还在），或把 QoS2 会话状态持久化到磁盘；PUBREL 才能找到 mid。
2. 不要用 QoS2 来替代业务幂等；生产上更稳的是 **QoS1 + 幂等键**（本项目 `(zone, drive, ts, seq)`）。
3. Broker 侧 `persistence true` / `session_present=1` 只能保住 Broker 的半边，保不住客户端的半边。

**面试口径**：

> “QoS2 协议上不应该丢；这次丢 1 条是 paho 的实现缺陷，不是 Broker 丢的。抓包能看到：断线前订阅端已经回了 PUBREC，但还没收到 PUBREL；重连 CONNACK 的 `session_present=1`，Broker 从 PUBREL 继续，新 paho Client 里没有这个 Packet ID 的记录，paho 直接回 PUBCOMP 避免挂住，消息就丢了——源码注释自己写着 ‘thus losing a message’。`clean_session=false` 只让 Broker 保留会话，不会让客户端把 QoS2 状态落盘。QoS2 在会话状态完整时是不丢不重的；这次是客户端状态没保住。QoS1 不会，因为 on_message 在 PUBLISH 时就调用了，Broker 重发后新 Client 还能收到，重复由幂等键挡掉。”

### 2.13 换 Broker 会不同吗：EMQX vs mosquitto 实测

**会不同，但别把它当成“EMQX 的 QoS2 更可靠”的证据。**

同一套 `qos_lab.py`（300 条 @100/s，第 1.0 秒断 1.5 秒），换 Broker 跑：

| Broker | QoS2 结果 | 重连时 Broker 发了什么 | 为什么 |
|---|---|---|---|
| mosquitto 2.1.4 | **299/300，missing [99]** | `PUBREL (Mid: 100)` | 断线前已收到订阅端 PUBREC，Broker 从 PUBREL 续；新 Client 没有 `_in_messages[100]`，paho 回 PUBCOMP 后丢 |
| EMQX 5.8.4 | **300/300**（6 次：1.0×4、1.5、2.0） | `PUBLISH (d1, q2, r0, m101)` | 断线时这条消息还没被订阅端 PUBREC，Broker 仍在“PUBLISH pending”阶段；重连后带 DUP=1 重发 PUBLISH，新 Client 收下并交付 |

EMQX 的 debug trace：

```text
Received CONNACK (1, 0)                 # session_present=1
Sending SUBSCRIBE ...
Received PUBLISH (d1, q2, r0, m101)     # DUP=1，重发 PUBLISH，不是 PUBREL
Sending PUBREC (Mid: 101)
...
Received PUBREL (Mid: 101)
Sending PUBCOMP (Mid: 101)
```

**关键区别不是“EMQX 更神”，而是断线落在 QoS2 的哪一段**：

- 落到“PUBLISH 还没被 PUBREC” → Broker 重发 PUBLISH → 新 Client 能交付；
- 落到“PUBREC 已收到、PUBREL 还没到” → Broker 发 PUBREL → 新 Client 没状态 → paho 丢；
- 我们的 EMQX 运行刚好落在前一段，mosquitto 运行刚好落在后一段。

**所以 EMQX 不是免疫**：如果 EMQX 已经收到 PUBREC 并保留了该状态，它同样会发 PUBREL，paho 新 Client 同样会丢。这次 6 次 0 丢失，是时序 + EMQX 的投递/重试行为共同造成的，不是协议保证。

**Broker 实现确实会影响结果**，常见的差异点：

| 差异点 | 影响 |
|---|---|
| 会话持久化（内存 vs 磁盘 / durable session） | Broker 重启后 QoS2 在途状态还在不在 |
| session expiry（MQTT 5 `session_expiry_interval`） | 断太久会话过期，队列被丢 |
| `max_inflight` / `max_mqueue_len` | 在途窗口、离线队列上限；超了会丢 |
| 重试/确认超时（EMQX `retry_interval`、`await_rel_timeout`；mosquitto `retry_interval`） | 什么时候重发、什么时候放弃 |
| session takeover 策略 | 同 client_id 重连时旧会话怎么处理 |
| PUBREC 后是否保留 payload | 决定重连时能不能重发 PUBLISH |

**公平比较的做法**：不要靠“随机断线”碰运气，而是**强制卡在 PUBREC→PUBREL 窗口**（例如给订阅端加固定延迟 / 在 PUBREC 后暂停），再对比各 Broker 是重发 PUBLISH 还是 PUBREL。否则你测到的是“这次断线落在哪一段”，不是 Broker 的 QoS2 能力。

**对本项目**：

- 不需要为了这个 1 条去换 Broker；根因是客户端状态，不是 mosquitto。
- 边缘继续用 mosquitto（2–7MB RSS）足够；EMQX 的价值在连接限速、每客户端指标、集群，不在“QoS2 魔法”。
- 数据面仍然建议 **QoS1 + 幂等键**；QoS2 的实验结论当成“理解协议边界”的素材，不要当成生产可靠性方案。

**面试口径**：

> “Broker 实现会不同：mosquitto 重连时从 PUBREL 续，paho 新 Client 丢了状态就丢 1 条；EMQX 这次重发了 PUBLISH（DUP=1），所以 300/300。但这不是 EMQX 的 QoS2 更强，而是断线时消息所处的握手阶段不同；如果 EMQX 已经收到 PUBREC 并保留状态，它也会发 PUBREL，同样会丢。要公平比较，得强制卡在 PUBREC→PUBREL 窗口；根本解法还是客户端状态持久化，或者 QoS1 + 幂等。”

## 3. 数据模型

> 导图原句：
> - 主键 (zone, drive, ts, seq) = 幂等键
> - hypertable：逻辑一张表，物理按时间切 chunk
> - 唯一约束只在 chunk 内 → 主键必须带 ts
> - 连续聚合 telemetry_1m（增量刷新）
> - 保留：原始 7 天 / 聚合 90 天，drop chunk 不 DELETE
> - 压缩：chunk 级列存，segmentby=(zone,drive)
> - 压缩实测 35MB → 5.8MB（约 6 倍）
> - 压缩会持锁：与全表 max(ts) 互锁，实测等 5 分钟
> - 小数据量下 hypertable 不比普通表快（8.4 vs 11.3ms）

### 3.1 主键 = 幂等键

```sql
PRIMARY KEY (zone_id, drive_id, ts, seq)
```

- **为什么不是只用 `drive_id`**：六个区里都有 `D01..D06`，只用 `drive_id` 会撞。第一版就是这么挂的（`code/ingest/README.md`）。
- **`seq` 从哪来**：设备应用层自增，**MQTT 不生成**。MQTT 只有 packet identifier（1–65535，逐连接循环复用），用于 QoS1/2 的确认匹配，没有业务含义，不能拿来排序或去重。
- **`seq` 的边界**：模拟器里是 36 台设备全局自增，只能保证“同一设备内单调”，不保证每台连续；真实设备通常每台自己从 0 开始。幂等键里带了 `(zone, drive)`，所以不要求全局唯一。
- **`ts` 与 `seq` 不一定同向**：NTP 校时/时钟回拨会让 ts 倒退；设备重启会让 seq 归零；ts 精度只有秒时同一秒多条靠 seq 区分。PoC 没做 `boot_id`、也没存 `received_at` 双时间轴，这是已知简化。

**幂等的实际效果**：WBS P3-2 验收“同 ts+seq 连发两轮共 100 条 → 表里仍 50 行”；P9-1 断流 3 次 0 丢 0 重；本次复核的中心库窗口 `count(*) = count(distinct 主键)`，重复为 0。**“不重”是这条主键挡的，不是 MQTT 挡的。**

### 3.2 hypertable 与 chunk

```sql
SELECT create_hypertable('telemetry', 'ts', chunk_time_interval => INTERVAL '1 hour');
```

- 逻辑上一张 `telemetry`，物理上按 `ts` 切成很多 chunk 表；查询带时间谓词时，planner 只扫相关 chunk（`ChunkAppend`）。
- **唯一约束只在 chunk 内**：TimescaleDB 要求唯一索引包含分区列 `ts`。因为主键里已经有 `ts`，同一条记录永远落在同一个 chunk，所以幂等仍然成立。**如果主键不含 `ts`，跨 chunk 就无法全局唯一**——这是“主键必须带 ts”的真正原因。
- 边缘 chunk 1 小时、中心 chunk 1 天：边缘要频繁 drop 7 天前数据，chunk 小一点淘汰更细；中心写入集中、保留久，chunk 大一点减少数量。
- **本次复核**：边缘 35,274,329 行 / 32 个 chunk（首尾时间跨约 33 小时，中间有停采/重启），0 个已压缩（数据还没到 7 天）；`hypertable_size` 5727MB。

**一个必须知道的坑**：

```sql
select pg_total_relation_size('telemetry');  -- 24 kB（父表，不含 chunk）
select hypertable_size('telemetry');         -- 5727 MB（真实大小）
```

面试如果让你“看下表多大”，用错函数会闹笑话。`deploy/scripts/pg-perf.sh` 和 `diag.sh` 用的是 `hypertable_size`，是对的。

### 3.3 连续聚合与查询路径

```sql
CREATE MATERIALIZED VIEW telemetry_1m
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 minute', ts) AS bucket,
       zone_id, drive_id,
       avg(speed_mps) AS speed_avg,
       max(current_a) AS current_max,
       avg(temp_c)   AS temp_avg,
       count(*)      AS samples
FROM telemetry
GROUP BY bucket, zone_id, drive_id
WITH NO DATA;
```

策略：`start_offset 3 days`、`end_offset 1 minute`、`schedule_interval 1 minute`。也就是每分钟刷新最近 3 天、到“上一分钟”为止。

API 的查询路径（`code/api/main.py:212-240`）：

| 窗口 | 数据源 | 点数（单驱动） | 为什么 |
|---|---|---|---|
| 60s | `telemetry` 原始 | 600 | 短窗口要精度 |
| 5m | `telemetry` 原始 | 3,000 | 仍可直绘 |
| 1h | `telemetry_1m` | 60 | 长窗口不需要秒级 |
| 6h | `telemetry_1m` | 360 | 同上 |
| 24h | `telemetry_1m` | 1,440 → LTTB 1,000 | 聚合后仍多于像素 |

**两个容易说错的点**：

1. **LTTB 在当前 UI 主路径只对 24h 生效**（1,440 → 1,000）。`api/README` 说的“36,000 → 1,000”是**函数级验证**（1h 原始点），不是当前 `/api/series?window=1h` 的路径——1h 走聚合只有 60 点，根本不需要 LTTB。ADR-0003 在 2026-11-20 的修订里也承认了这一点。
2. **LTTB 只用于画线**，任何平均值、最大值、告警判定都不许拿抽样点算。这是“保形不保统计”的边界。

**聚合的坑**：`start_offset 3 days` 意味着 3 天前的迟到原始点不会刷新进聚合；而原始保留 7 天。PoC 没处理“3–7 天迟到数据”，属于产品化待补。

### 3.4 保留与压缩：两个策略的阈值撞了

```sql
SELECT add_retention_policy('telemetry',    INTERVAL '7 days');
SELECT add_retention_policy('telemetry_1m', INTERVAL '90 days');
SELECT add_compression_policy('telemetry',  INTERVAL '7 days');
```

- 保留用 `drop_chunks`，不是 `DELETE`：`DELETE` 产生大量死元组、要 vacuum、表文件不缩；`drop_chunks` 直接删文件，毫秒级。C-PIPE-007 实测：删 30 分钟 64.7 万行，`DELETE` 254ms、表仍 338MB；`drop_chunks` 11ms、降到 324MB。
- **保留是 chunk 粒度**：7 天保留实际可能留到 7 天 + 最多 1 小时（边缘 chunk 1h），不是精确到秒。
- **压缩和保留都设 7 天 = 压缩窗口≈0**：chunk 刚满 7 天就同时满足“可压缩”和“可删除”。压缩任务每 30 分钟跑、保留任务每天跑；谁先跑，另一个就白干。本次复核边缘库 **0 个已压缩 chunk**，也印证了当前数据还没走到这条路径。**“35MB → 5.8MB 约 6 倍”是 C-PIPE-007 在独立 2M 行表上的实验结果，不是当前这套 7 天保留策略的线上收益。**
- 要说压缩收益，得先把保留拉长（比如原始 30 天）或把压缩提前（比如 1 天），让压缩后的 chunk 真正留下来。

**压缩参数为什么这么设**：

```sql
ALTER TABLE telemetry SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'zone_id, drive_id',
    timescaledb.compress_orderby   = 'ts DESC'
);
```

- `segmentby` 必须包含 `zone_id`：`D01..D06` 在 6 个区都有，只按 `drive_id` 分段会把 6 个区混在一段里，查单区要解压更多。
- `orderby ts DESC`：时间近的先出，范围查询少解压。
- **压缩会持锁**：`compress_chunk()` 对该 chunk 取强锁；如果同时有全表 `max(ts)`（不带时间谓词），会互锁。RB-03 记录“压缩本身从几秒变成等了 5 分钟才拿到锁”。处置：只压冷 chunk、水位查询带时间谓词、别在高峰压。

**但代码里还在写全表 `max(ts)`**：

| 位置 | SQL | 影响 |
|---|---|---|
| `code/ingest/main.py:325` | `select max(ts) from telemetry` | 只在启动跑一次，可接受 |
| `code/api/main.py:177` | `select max(ts) as wm from telemetry` | `/healthz` 每次请求都跑；前端 `usePoll('/healthz', 5000)` 每 5s 一次 |
| `code/forwarder/main.py:55` | `select max(ts) from telemetry where site_id = %s` | 启动一次；仍扫所有 chunk |

这正是 RB-05 警告的“水位查询别写全表 max(ts)，加 `where ts > now() - interval '1 day'` 让 chunk 裁剪生效”。**面试被问“你文档说别这么写，代码怎么还这么写？”** 答：“启动时一次可以接受；api 的 /healthz 每 5 秒一次是 PoC 的欠账，产品化会改成缓存水位或带时间谓词。这个矛盾我在复核时发现了，没来得及改。”

### 3.5 小数据量下 hypertable 不一定更快

C-PIPE-007（同一份 2,000,000 行、338MB，本机）：

| 测试 | 普通表 + ts 索引 | hypertable（10 分钟 chunk） |
|---|---|---|
| 5 分钟窗口 `count(*)` | **8.4 ms** | 11.3 ms（规划开销） |
| 删除 30 分钟数据（64.7 万行） | DELETE 254ms，表仍 338MB | `drop_chunks` **11ms**，降到 324MB |
| 压缩 | 无 | **35MB → 5.8MB（约 6×）** |
| 唯一约束 | 全表 | 每 chunk 内（PK 必须含时间列） |

**方向不要讲反**：8.4ms 是**普通表**，11.3ms 是 **hypertable**。导图和 README 的表只写“8.4 vs 11.3”，容易被听成“hypertable 8.4 更快”。正确说法：“小数据量下普通表反而略快；hypertable 的价值在 drop/压缩/索引规模，不在单次查询。”

**边界**：这是 2M 行、10 分钟 chunk 的结论；当前边缘库 35M 行、1 小时 chunk，没有重跑对比。别把 2M 行的结论外推到 35M 行——只能说“1e7 行以内基本持平”，35M 已经超出验证范围。

### 3.6 这一节的讲法（40 秒）

> “模型上最关键的是幂等键 `(zone, drive, ts, seq)`。`zone` 不能省，因为六个区都有 D01–D06；`seq` 是设备自增，不是 MQTT 的 packet id。存的是 TimescaleDB hypertable：逻辑一张表，物理按时间切 chunk，查询能裁剪。唯一约束是每个 chunk 一个，但主键带了 ts，同一条记录永远落同一个 chunk，所以幂等仍然成立。长窗口查 1 分钟连续聚合，1 小时只有 60 个点，不需要 LTTB；LTTB 只在 24 小时聚合 1440 点降到 1000 时用。保留用 drop_chunks 不用 DELETE，压缩是 chunk 级列存、按 zone+drive 分段。这里有个我复核出来的配置问题：压缩和保留都设 7 天，压缩窗口约等于 0，6 倍压缩是实验表的结果，不是线上收益。”

**高频追问**

| 问 | 答 |
|---|---|
| 为什么主键带 ts？ | 唯一索引必须包含分区列；否则跨 chunk 无法全局唯一。 |
| seq 会回绕吗？ | 设备侧 bigint，PoC 不会；真设备要考虑重启归零，所以键里还有 ts。 |
| 1 小时窗口为什么只有 60 点？ | 查的是 1 分钟聚合，不是原始 36,000 点；原始点只用于 ≤5 分钟。 |
| LTTB 会丢峰值吗？ | 保形不保统计；峰谷通常保留，但平均值/告警判定不许用抽样点。 |
| 为什么压缩和保留都 7 天？ | 这是配置矛盾：压缩窗口≈0；应该保留 30 天或压缩提前到 1 天。 |
| 表多大？ | 用 `hypertable_size`，不是 `pg_total_relation_size`；当前 5.7GB / 35M 行。 |

## 4. 写入路径

> 导图原句：
> - MQTT 逐条到 → 内存 buffer → 批量写
> - 批量 200 行 / 1 秒，一次 commit
> - 逐条提交 501 行/秒
> - executemany 44,521 行/秒
> - COPY 临时表 56,682 行/秒（但不能 ON CONFLICT）
> - 瓶颈是 commit 次数（WAL fsync），不是 SQL
> - RPO ≈ 1 秒；SIGTERM 会先 flush
> - 要 RPO=0：手动 ACK 或先落盘 WAL

### 4.1 从 MQTT 到落库的完整路径

`code/ingest/main.py`：

```
paho 线程 on_message()
  ├─ 解析 JSON → row
  └─ state_lock:
       ├─ wal_append(line)      # 写文件（buffering=0，进 page cache）
       └─ buffer.append(row)    # 内存 buffer

主循环（每 0.2s 检查）:
  due_rows = len(buffer) >= 200
  due_time = now - last_flush >= 1.0
  if due_rows or due_time: flush()

flush():
  flush_lock:
    state_lock: rows, buffer[:] = list(buffer), []; end = wal_fh.tell()
    wal_sync()                  # fsync 整批
    conn.executemany(INSERT_SQL, rows)
    conn.commit()               # 一次 commit
    wal_commit(end)             # 推进游标（写 wal.commit + fsync）
```

关键数字：

- 360 点/秒 → 200 行约 0.56s 攒满，所以**大多数批次是 200 行**；低流量时才是 1s 超时触发。
- 每秒 commit 约 **1.8 次**（360/200），不是 360 次。
- `BATCH_ROWS` / `BATCH_SECONDS` 都是环境变量，可调；`compose.yaml` 没显式设，用默认 200/1.0。

### 4.2 三种插入方式的实测

`scripts/bench_insert.py`（3 万行，同一张表）：

| 方式 | 耗时 | 吞吐 | 说明 |
|---|---|---|---|
| 逐条 execute + 逐条 commit | 59.9 s | **501 行/秒** | 每次 commit 触发 WAL fsync（约 2ms），全花在刷盘 |
| `executemany`，200 行/批，每批一次 commit | 0.67 s | **44,521 行/秒** | 本项目选它；89 倍于逐条 |
| `COPY` 进临时表 → `INSERT ... SELECT ... ON CONFLICT` | 0.53 s | **56,682 行/秒** | 最快，但 COPY 不能直接 ON CONFLICT，失败处理复杂 |

**结论**：瓶颈是**提交次数**，不是 SQL 解析。3 万行拆成 3 万次 commit，比批量慢 89 倍。

**为什么不用 COPY**：360 行/秒的量级，`executemany` 有几十倍以上余量（纯插入口径百倍）；COPY 要多一张临时表、要处理去重、失败恢复更麻烦。历史数据导入（百万行、可接受短暂锁）才值得上 COPY。

**“100 倍余量”的口径要小心**：44,521 / 360 ≈ **124 倍**，但这是纯插入 benchmark；端到端 ingest 的实测约 **1.3 万行/秒**（ADR-0006），对 360/s 只有 **36 倍**。面试说“批量插入有百倍余量、端到端几十倍余量”更准确；说“吞吐有 100 倍余量”容易被追问“端到端测过吗”。

### 4.3 WAL：把“失败才落盘”改成“先落盘再入库”

第一版是“flush 失败才写 spool”，问题：进程在 flush 前被 `kill -9`，内存里那 ≤200 行就没了。改成 WAL 后：

1. `on_message` 先追加 WAL（写文件，无缓冲，进 page cache）；
2. flush 时 `fsync`，再入库，最后推进 `wal.commit` 字节偏移；
3. 崩溃后从偏移回放，`executemany` 500 行一块，坏行 `try/except` 跳过；
4. 重复由主键挡掉，所以回放可以“至少一次”。

C-PIPE-009 实测（500 条消息，`kill -9` ingest）：

| 阶段 | 行数 |
|---|---|
| 发送前 | 0 |
| kill -9 时（已 flush） | 315 |
| 重启回放后 | **500** |

日志出现 `crash tail recovered`，WAL 游标从最后提交位置继续。

**为什么 kill -9 不丢**：进程死了，但 page cache 还在，内核会把已 `write()` 的数据留在文件里；重启 `open` 读得到。**为什么断电可能丢**：`fsync` 在 flush 时做，最后 ≤1s 的 `write()` 可能还在 page cache，没落盘。

**WAL 的其他细节**：

- `wal_commit` 只许前进（`max(offset, wal_committed_bytes)`），防止回放把游标写退。
- `wal_compact`：已提交部分超过 64MB 就把文件重写，只留未提交尾部；否则 WAL 会无限长。
- `wal_pending()` = 文件大小 - 已提交偏移；`/healthz` 暴露，持续涨 = 库写不进去。
- 回放和 flush 用 `flush_lock` 互斥；`on_message` 和 buffer 追加用 `state_lock` 原子。

### 4.4 库挂了会怎样

`flush()` 的异常分支（`code/ingest/main.py:226-234`）：

- 不推进 `wal_commit`，WAL 就是缓冲；
- `conn.rollback()`，标记 `_db_down = True`；
- 后台 `replay_loop` 每 2s 重试 `wal_replay()`；
- 恢复后写一条 `events(kind=db_recovered)`。

**内存不会涨**：flush 先把 buffer 整体取走（`rows, buffer[:] = list(buffer), []`），失败也不放回；数据已经在 WAL 里。所以库挂 1 小时，涨的是磁盘（约 190–230MB/小时），不是内存。这是 WAL 设计的一个好处。

**磁盘没有上限**：代码没做“WAL 超过 N GB 就拒收/降级”的保护。需求文档把“spool 撑爆边缘磁盘”列为风险 #4；PoC 没实现。面试被问“断网 24 小时怎么办”，答：“360 点/秒 × 24h ≈ **3,100 万行**，按每行约 150–180B 算，WAL 约 **4.5–5.5GB**；边缘盘要先算容量，产品化要加磁盘水位告警/降采样/拒收策略，PoC 没做。”

**看门狗两级**（`code/ingest/main.py:385-397`）：

| 级 | 依据 | 能发现 | 处置 |
|---|---|---|---|
| ① 线程死亡 | `Thread.is_alive()` | 未捕获异常退出 | 新建 Thread（Thread 不能 restart） |
| ② 线程卡死 | `replay_tick` 心跳 | 活着但卡在 IO | Python 杀不了线程 → `os._exit(3)`，docker `restart: unless-stopped` 拉起，WAL 回放补数据 |

`psycopg.connect(..., connect_timeout=5)` 防止连接阶段无限挂起。**退出码 3 是看门狗专用，RB-03 的退出码表里没写**——面试如果被问“3 是什么”，答“replay 卡死主动退出，让 supervisor 重启”。

### 4.5 RPO 与 SIGTERM

- `RPO ≈ 1s`：flush 间隔 1s；最坏丢最后 1s 的**未 fsync** 数据（断电）。
- `docker stop` 发 SIGTERM → `_on_sigterm` 抛 `KeyboardInterrupt` → `except KeyboardInterrupt: flush()` → 正常退出。所以 `docker stop` 不丢。
- `docker kill -9` 不丢：page cache + WAL 回放。
- 要 RPO=0：每条消息 fsync（太贵），或手动 ACK + 设备保留到业务确认（PoC 没做），或先落盘 WAL 再回 ACK（也要 fsync）。**PoC 的取舍是“进程崩溃不丢、断电最多 1 秒”**。

### 4.6 这一节的讲法（35 秒）

> “写入路径是 MQTT 逐条到、内存 buffer、满 200 行或 1 秒批量写。三种插入方式我测过：逐条 commit 501 行/秒，executemany 44,521，COPY 56,682；差 89 倍，瓶颈是 commit 的 WAL fsync，不是 SQL。我们选 executemany，360 行/秒有几十倍余量。更关键的是 WAL：每条先追加 WAL，flush 时 fsync、入库、推进游标；kill -9 之后从游标回放，500/500 不丢。代价是断电仍可能丢最后 1 秒，因为 fsync 在 flush 时做。库挂了也不丢：flush 失败不推进游标，WAL 就是缓冲，内存不会涨，涨的是磁盘。”

**高频追问**

| 问 | 答 |
|---|---|
| 为什么 200 行 / 1 秒？ | 200 行约 0.56s 攒满；1s 是低流量兜底。延迟 <1s，commit 次数约 1.8/s。 |
| 为什么不用 COPY？ | 不能直接 ON CONFLICT；360/s 用不上；历史导入才值得。 |
| WAL 会不会无限长？ | 已提交超过 64MB 会 compact，只留未提交尾部。 |
| 库挂 1 小时会怎样？ | WAL 涨约 190–230MB，内存不涨；恢复后回放；磁盘没上限，是已知风险。 |
| 为什么 kill -9 不丢、断电会丢？ | page cache 在进程死时还在；断电时未 fsync 的页丢失。 |
| 退出码 3 是什么？ | replay 线程卡死，看门狗 `os._exit(3)` 让 docker 重启。 |

## 5. 断流与恢复

> 导图原句：
> - 三段责任：设备 / broker 会话 / ingest
> - 设备侧 spool（ndjson）+ 恢复补发
> - ingest spool：库挂了整批落盘
> - forwarder 水位 + 120s 重叠回扫
> - 迟到行陷阱：只按 ts>水位 会漏 184 条
> - 实测：断 60s，0 丢 0 重，1s 追平

### 5.1 三段责任（再强调一次）

| 段 | 断的是谁 | 谁兜底 | 代码 |
|---|---|---|---|
| 设备 → Broker | 现场网络 | 设备自己 | `code/simulator/main.py:82-133` |
| Broker → ingest | ingest 重启 | Broker 持久会话 | `code/ingest/main.py:340-355` |
| ingest → DB | 库挂/进程崩 | ingest WAL | `code/ingest/main.py:89-165, 207-242` |

**PUBACK ≠ 落库**：QoS1 的确认只到 Broker。要做到端到端不丢，设备必须保留缓存直到收到业务层确认（或按时间窗保留）。模拟器是简化版：恢复即补发、补发完删缓存，没有等业务 ACK。真实设备要改固件。

### 5.2 设备侧 spool（模拟器扮演设备）

`code/simulator/main.py`：

- `--offline-at 5 --offline-for 8`：第 5 秒开始“断网” 8 秒；
- 断网期间不 publish，把 `{topic, payload}` 逐行写 `--spool`（默认 `/tmp/interroll-sim-spool.ndjson`）；
- 恢复后起后台线程，按 `--replay-rate`（默认 400 条/秒）限速补发，补完删文件；
- 不仅计划内断网，`connected` 事件掉了也会触发 spool 回放（`:135-157`）。

**为什么 NDJSON**（`code/ingest/README.md`）：

| 维度 | NDJSON | 一个大 JSON 数组 |
|---|---|---|
| 追加一条 | 末尾写一行 | 要重写整个文件 |
| 读取 | 逐行流式，内存 O(1) | 必须先解析全文 |
| 崩溃 | 最多坏最后一行 | 整个文件不可解析 |
| 排查 | `tail`/`grep` 直接看 | 得先跑解析器 |

C-PIPE-002 实测：200,000 行 / 15.7MB，补传 14.9s（约 13,400 行/秒），峰值 RSS **40MB**，与文件大小无关；落库 200,000 行全中。

**但注意**：这份实测对应的是旧版 ingest 的 `replay_spool()`；现在 ingest 已经改成 WAL，`scripts/bench_spool.py` 还在 import `SPOOL_DIR` / `replay_spool`，**跑不起来**（见 §12）。历史数字可以参考，复现要改脚本。

### 5.3 ingest 的“spool”现在是 WAL

导图说“ingest spool：库挂了整批落盘”。**当前实现没有独立的 spool 文件**：`on_message` 已经先把每行追加到 WAL，flush 失败只是不推进游标，WAL 自然就是缓冲。P3 的 WBS 还写着“掐断 DB 连接时 ingest 侧落 6 个 spool 文件”“spool_rows 归零”，那是 WAL 重构前的验收记录。

**面试口径**：“最早是失败才落 spool，后来改成先写 WAL——因为失败才落盘会丢掉进程崩溃前那 ≤200 行。现在 WAL 同时兼任 spool，少一套状态。”

### 5.4 forwarder 的水位 + 120s 重叠回扫

`code/forwarder/main.py`：

- 水位 = **中心库** `max(ts) where site_id = S1`（`:53-61`）；重启自动续传，不另存状态。
- 首次启动 `START_WINDOW=600s`：只回放最近 10 分钟，避免把边缘历史全量拉到中心。
- 正常推进：`select ... from telemetry where ts > 水位 order by ts limit 500`，插入中心，`watermark = rows[-1][0]`。
- 重叠回扫：`gap_from = watermark - 120s`、`gap_to = watermark`，`ts > gap_from and ts <= gap_to`，每批 500；重复由 `ON CONFLICT` 挡掉。**但代码里只在启动、或“边缘 30 秒没有新行”时才 re-arm，不是严格每 30 秒跑一次**；连续流量下不触发，见 §12.1。
- 中心挂了：异常分支 `watermark` 不动，2s 后重连，恢复后从水位续推。

ADR-0007 实测：

| 项 | 结果 |
|---|---|
| 中心停止 60 秒 | forwarder 报错重试，水位不动 |
| 恢复后追平 | **1 秒** |
| 窗口 25,668 条 | 边缘 25,668 / 中心 25,668 / 重复 0 / 缺失 0 |
| 迟到行缺陷 | 修复前窗口少 184 条，重叠回扫后为 0 |

**但本次复核发现：稳态下仍有约 0.2% 的漏行。** 这是这份材料里最重要的“别背错”的一条，单独放 §12.1 讲。

### 5.5 迟到行陷阱：为什么只按 `ts > 水位` 会漏

C-PIPE-006 的解释：设备时钟抖动 + ingest 批量落库顺序，使部分 `ts` 较小的行在心跳推进后才入库；水位一旦越过它，就永远不会再被读到。120s 重叠回扫就是为这个加的。

**但更准确的说法是**：不只是“ts 更小的迟到行”，**同一个 ts 的行也会被拆成两批提交**。ingest 的 flush 是 200 行一次，而一拍是 36 行；200 不是 36 的整数倍，flush 边界经常切在一拍中间。forwarder 如果在第一批提交后就读到这一拍，会把 `watermark` 推到该 ts；第二批同 ts 的行随后到达，`ts > watermark` 永远为 false，就漏了。

这解释了我复核到的现象（§12.1）：缺失行总是聚在**单个 ts**，且中心库保留了该 ts 的前若干行、缺后面的连续 seq。**根因是“用 ts 当游标”，不是“ts 大小/时钟抖动”。**

### 5.6 断流 60s 的实测与口径

P9-1 / ADR-0007 的结论：

- 断 60s，0 丢 0 重；
- 恢复后 1s 追平（边缘→中心）；单线断流追平 10.6–16.7s（瓶颈是重连退避，C-PIPE-003）；
- 窗口 25,668 条逐条对齐。

**口径要主动交代**：

1. 这是**闭合窗口**比对，不是“全表行数差”；
2. 比对键是 `(zone, drive, ts, seq)`，不是 `count(*)`；
3. 断流期间两端的**写入速率**要一致，否则窗口边界会差；
4. 这个结果在“停中心期间 watermark 不动、恢复后从旧水位续推”的路径下成立；同一 ts 被拆批的迟到行仍要靠回扫，而回扫在连续流量下不跑（§12.1）。

### 5.7 这一节的讲法（40 秒）

> “断流我分三段讲：设备到 Broker，设备自己 spool，恢复限速补发；Broker 到 ingest，靠 clean_session=false + 固定 client_id 让 Broker 排队；ingest 到库，靠 WAL，先落盘再入库，kill -9 也不丢。跨机是第四段：边缘库到中心库，不用 bridge，用 forwarder 按水位推，加 120 秒重叠回扫补迟到行。实测停中心 60 秒，恢复 1 秒追平，窗口 25,668 条 0 丢 0 重。这里有个我复核出来的边界：水位只用 ts 做游标，稳态下同一 ts 的行分两批提交会漏，约 0.2%；60 秒演练因为回扫把这批补上了，所以没暴露。修法是把游标换成边缘行号或周期性短回扫。”

**高频追问**

| 问 | 答 |
|---|---|
| 断网 60 秒为什么 1 秒追平？ | 数据在边缘库，forwarder 只推增量；水位没动，恢复后从水位续推。 |
| 设备 spool 补完就删，会不会丢？ | 会，如果补发后进程崩、Broker 没收到；真实设备应保留到业务 ACK，PoC 简化了。 |
| 120s 回扫会不会重复写？ | 会重复读，但 `ON CONFLICT` 挡掉，不重复写。 |
| 回扫窗口为什么是 120s？ | 要覆盖最大乱序量；实测乱序只有几秒，120s 是保守值。太大浪费扫描。 |
| forwarder 会不会成为单点？ | 会；PoC 单实例，产品化要主备/多实例，但水位会打架（ADR-0002 的代价）。 |

## 6. 多机与重连风暴

> 导图原句：
> - fleet.py：每台设备一条独立连接
> - offset 模式：jitter 0/3/10 → 峰值 664/248/44
> - full jitter：峰值更低（67/51），恢复更慢
> - 抖动是峰值换时长，不是减少负载
> - 厂商边界：设备固件可写契约，平台只能限流+排队

### 6.1 为什么要有 fleet.py

| 脚本 | 模拟什么 | 连接数 | 用途 |
|---|---|---|---|
| `code/simulator/main.py` | 一台网关聚合 36 台驱动 | **1 条**连接、36 个 topic | 单线断流、日常造数 |
| `code/simulator/fleet.py` | N 台设备各自连 Broker | **N 条**连接 | 才能制造重连风暴 |

`fleet.py` 每台设备一个线程、一条 `mqtt.Client`、`client_id=dev-{idx}`、`qos=1`。默认 `--devices 36`，风暴实验用 360。

`scripts/chaos_multi.py` 的做法：

1. 起 `fleet.py`，等 `stagger + 8s` 让设备陆续接入；
2. 用 paho 订 `$SYS/broker/clients/connected`，1s 采样；
3. `docker stop` Broker 10s，再 `docker start`；
4. 算 `peak_reconnect_per_s`（恢复后每秒净增连接的峰值）、`recover_s`（回到基线 95% 的时间）、`min_connected_after_restart`、`broker_running`。

### 6.2 抖动是“峰值换时长”，不是“减少负载”

数据在 §2.4，这里只记结论和口径：

- jitter 0 → 峰值 664/s、1.3s 恢复；
- jitter 10 → 峰值 44/s、19.5s 恢复；
- 峰值和恢复时间大致**反比**，总重连次数没有变。
- full jitter 在 jitter=3 时峰值 67/s（明显低于 offset 的 248/s），但 jitter=10 时 51/s 反而略高于 offset 的 44/s；恢复也更慢（22.7s vs 19.5s）。**没有“full 一定更好”**。

**指标口径的坑**：`peak_reconnect_per_s` 是 `clients/connected` 的净增量，不是 Broker 的 accept 次数。设备快速重连又掉线时，净增量会低估风暴；要更准，得读 Broker 日志或 EMQX 的 `client.connected` 事件。`chaos_multi.py` 还特意跳过 `dt < 0.5s` 的采样，避免 `$SYS` 同秒连发把速率放大成假峰值。

### 6.3 厂商边界：平台能做什么、不能做什么

导图这句是全篇最“产品经理”的一句，面试很加分：

| 能做 | 不能做 |
|---|---|
| 定契约：固定 client_id、`clean_session=false`、指数退避 + 抖动、补传限速、设备缓存到业务 ACK | 改设备固件 |
| Broker 侧限流、排队上限、连接数上限 | 保证现场网络 |
| 平台侧幂等、WAL、水位 | 让设备“不重连” |

真实项目里，设备固件是厂商的；平台只能**定义接入契约 + 在平台侧兜底**。PoC 里模拟器扮演设备，所以能演示 spool；换成真 PLC，这部分要厂商配合。面试如果被问“设备不配合怎么办”，答：“平台侧至少做到幂等 + 限流 + 可观测；设备侧契约写进接入规范，不配合就只能接受更大的 RPO。”

### 6.4 量级演进：S/M/L/X 会依次暴露什么

`docs/01-需求.md` 的分档，面试可以拿来答“如果量级涨 10 倍”：

| 档 | 驱动数 | 消息速率 | 每天行数 | 断网 1h spool | 主要瓶颈 |
|---|---|---|---|---|---|
| S 单线 | 36 | 360/s | 3,110 万 | ~190 MB | 无明显瓶颈（当前验证档） |
| M 单站点 | 360–1,080 | 3.6k–10.8k/s | 3–9 亿 | 2–6 GB | ingest 单进程写入、Broker 单实例 |
| L 大型 DC | 1,800–3,600 | 18k–36k/s | 15–31 亿 | 10–20 GB | 单库写不动，必须边缘聚合 + 分片 |
| X 多站点 | ×站点数 | 叠加 | ×N | ×N | 重连风暴、中心带宽、时钟漂移 |

**问题暴露顺序**（需求文档列的 6 条）：

1. 重连风暴（站点级断网恢复）；
2. 单进程 ingest 写不动（> ~1.5 万行/秒，lag 持续涨、spool 只增不减）；
3. 单库容量/chunk 爆炸（> 3 千万行/天，查询慢、压缩跟不上、备份窗口拉长）；
4. spool 撑爆边缘磁盘（断网 >1h 且 ≥M 档，磁盘满 → ingest 与库一起挂）；
5. 时钟漂移放大（设备数 > 数百，同一秒数据分散、聚合桶边界抖动）；
6. WS 广播成本（并发看板 >20，单帧点数 × 客户端数）。

**演进路径**（不是 PoC 要做的）：边缘聚合后再回传、按站点分库/分片、Broker 集群、WS 服务端共享快照 + 按客户端降采样。面试说“我知道会在哪一步先崩，以及为什么不在这台机器上演 L 档”比“我能支持无限扩展”可信。

### 6.5 这一节的讲法（30 秒）

> “多机实验我用 fleet.py，每台设备一条独立连接，360 台。停 Broker 10 秒再拉起，用 `$SYS/clients/connected` 1 秒采样。jitter 0 时峰值 664 条/秒，jitter 10 降到 44，但恢复从 1.3 秒拉到 19.5 秒——抖动是把峰值换成时长，不是减少总负载。full jitter 在 3 秒档更低（67 vs 248），但 10 秒档反而略高（51 vs 44），所以没有绝对更好，要先定恢复窗口。平台能做的只有定契约、限流、排队；改设备固件是厂商的事。”

**高频追问**

| 问 | 答 |
|---|---|
| 360 台设备真的都连上了吗？ | 基线连接 363（360 设备 + sampler + 其他），`$SYS` 可证。 |
| 为什么断 10 秒？ | 足够清空连接、又不至于让实验太久；生产要测 1–5 分钟。 |
| 重连风暴会把 Broker 打挂吗？ | 本次没挂（`broker_running=true`）；加 TLS 后握手更贵，峰值更危险，没测。 |
| 为什么不用 MQTT 5 的 session expiry？ | PoC 用 3.1.1 语义；5.0 的 `session_expiry_interval` 更细，但 Broker 支持要确认。 |
| 设备侧不做指数退避怎么办？ | 平台只能限流 + 排队；重连风暴时最先崩的是 Broker accept 队列。 |

## 7. 背压

> 导图原句：
> - 服务端 WS 10fps 节流
> - 前端 useLive 90ms 合并
> - useHistory 环形缓冲 120 点（丢旧值）
> - 实测：1856 点/秒仍 60fps、0 长任务
> - 前端抗的是渲染速率，不是数据速率

### 7.1 三层解耦

```
MQTT 实时帧（可能 2000 点/秒）
   │
   ▼
api /ws/live：每 100ms 发一帧全量快照（WS_FPS=10）
   │            └─ 客户端读不动：send 超时 2s → close(1013)
   ▼
前端 useLive：帧间隔 <90ms 直接丢（不是合并）
   │
   ▼
useHistory：只留最近 120 点（10Hz → 12 秒窗口），满则丢最旧
   │
   ▼
ECharts canvas：60fps 渲染
```

**核心结论**：前端能扛住的不是“数据速率”，而是“**渲染速率**”。只要服务端把推送压到固定帧率，后端涨到 2000 点/秒，浏览器仍是 60fps。

### 7.2 实测

C-PIPE-005（headless Chrome，1440×900，8 秒采样）：

| 灌入 | 消息速率 | fps 均值/最低 | 长任务 | WS 帧 | 丢失 |
|---|---|---|---|---|---|
| 空载 | —— | 60.3 / 60 | 0 | 10/s | —— |
| 50 台 × 10Hz | 464/s | 60.8 / 60 | 0 | 10/s | 0（16715/16715） |
| **200 台 × 10Hz** | **1856/s** | **60.5 / 60** | **0** | 9.9/s | 0（76108） |

注意 200 台 × 10Hz 理论是 2000/s，实测 1856/s：`fleet.py` 每台一个线程，调度/连接开销让实际发送略低于理论值。面试说“约 1900 点/秒”比“正好 2000”稳。

### 7.3 服务端：10fps + 2s 超时

`code/api/main.py:262-294`：

```python
interval = 1.0 / WS_FPS          # 默认 0.1s
while True:
    await asyncio.sleep(interval)
    snapshot = list(live.values())          # 36 点
    await asyncio.wait_for(ws.send_json(payload), timeout=2.0)
    # 超时 → ws_stats["timeouts"] += 1 → close(1013)
```

- 每帧发**全量快照**（36 点 ≈ 4.8KB，10fps ≈ 48KB/s），不是增量。重连第一帧即补齐，不需要断点续传。
- 背压最后一环：`await send` 在客户端读不动时会卡住；2s 超时即判定假死，`close(1013)`（Try Again Later），不会无限占着连接。
- **为什么不用 ping/pong**：10fps 本来就在持续发数据，发不出去就是最强的存活信号；再叠一层 ping/pong 只增加状态。半开连接最迟 2s 内被发现。
- 每个客户端一个协程，`live` 字典读锁保护；广播成本 = 帧大小 × 客户端数，线性上升。

### 7.4 前端：90ms 是“丢帧”，不是“合并”

`code/web/src/lib/api.ts:70-81`：

```ts
const now = performance.now()
if (now - last.current < 90) return
last.current = now
setPoints(frame.points ?? [])
```

- 这是**丢弃过密帧**，不是把多帧合并成一条。`last` 只在接受时更新，所以渲染更新频率上限约 11.1Hz。
- 被丢的帧不会补；屏幕最多显示“90ms 前的快照”。对 10Hz 数据足够。
- `useHistory` 用 `[...h.slice(...), newPoint]` 保留最近 120 点；功能上是环形缓冲，实现上是数组切片（O(n) 拷贝，120 点无感）。
- **历史走 `/api/series`**，不要拿实时帧攒长曲线；实时帧只用于“当前状态”。

### 7.5 并发看板与扩展

当前只验证了**单看板、单页面**。20 个看板时：

- 每帧 4.8KB × 10fps × 20 = 约 **1MB/s** 服务端出口；
- 每个客户端一个协程 + 一份 JSON 序列化；CPU 线性涨；
- 浏览器端各自 36 点，内存不涨太多。

产品化优化：
- 服务端只序列化一次，复用同一份 bytes 广播；
- 按客户端窗口降采样（长窗口不需要 10fps）；
- 大屏用 SSE/WS 二选一；20 个看板以内不需要消息队列。

### 7.6 这一节的讲法（30 秒）

> “背压分三层：服务端 WS 固定 10fps，前端 90ms 内的重复帧直接丢，useHistory 只留 120 点。实测 200 台设备 1856 点/秒灌进来，浏览器还是 60fps、0 长任务。关键不是前端多能算，而是服务端把推送压到固定帧率——前端抗的是渲染速率，不是数据速率。WS 发送 2 秒超时就 close(1013)，客户端读不动不会拖死服务端。并发 20 个看板没测，广播成本是线性的。”

**高频追问**

| 问 | 答 |
|---|---|
| 90ms 为什么不是 100ms？ | 比 10fps 略短，避免定时抖动导致整帧被丢；上限约 11Hz。 |
| 丢旧值还是丢新值？ | 实时帧丢的是“过密帧”，保留最新；历史缓冲满时丢最旧。 |
| WS 断了怎么办？ | 前端指数退避 + 抖动（500ms 起、上限 30s、±50%），重连第一帧全量补齐。 |
| 为什么每帧发全量？ | 36 点 4.8KB，全量最简单；增量要维护版本/丢包恢复，不值得。 |
| 2000 点/秒为什么不是 2000 帧？ | 服务端合并成 10fps 快照；点数/秒 ≠ 帧/秒。 |
| 20 个看板会怎样？ | 出口约 1MB/s，CPU 线性涨；没测，产品化要共享序列化 + 按需降采样。 |

## 8. 可观测与诊断

> - JSON 日志 + faulthandler + 容器日志上限 10m×3
> - events 表：启动/停库/恢复/补传

### 8.1 日志

`code/{api,ingest}/log_setup.py`（两份刻意重复，符合“复制小段代码优于抽象”）：

- 一行一条 JSON 到 stdout：`ts / level / svc / msg`，可选 `zone / drive / trace_id / rows / spool / detail`；
- `faulthandler.enable()`：段错误/死锁把栈打到 stderr，`docker logs` 能看到；
- 容器日志上限：`deploy/compose/compose.yaml` 的 `x-logging`，`max-size: 10m`、`max-file: 3`，每个容器最多 30MB，防止跑几个月写满边缘盘；
- 日志不落明文密码：compose 里 DSN 由环境变量拼，diag 的 `env.redacted` 过滤 `PASSWORD|SECRET|TOKEN`。

**一个细节**：`_EXTRA` 里还有 `"spool"`，但 WAL 重构后 ingest 不再打 spool 字段；属于历史残留，不影响功能。

### 8.2 events 表：只记“发生了什么”

```sql
CREATE TABLE events (
  ts timestamptz NOT NULL DEFAULT now(),
  kind text NOT NULL,
  severity text NOT NULL DEFAULT 'info',
  detail jsonb NOT NULL DEFAULT '{}'::jsonb
);
```

当前代码会写：

| kind | 何时 | 位置 |
|---|---|---|
| `ingest_start` | ingest 启动 | `code/ingest/main.py:336` |
| `ingest_stop` | SIGTERM 优雅退出 | `:401` |
| `db_recovered` | flush 从失败恢复 | `:225` |
| `wal_replayed` | 崩溃/断库后回放完成 | `:162` |

**文档漂移**：RB-03 和 P6 还写 `spool_replayed`，代码已经改名 `wal_replayed`；`db_down` 写不进去（库挂了），所以只在恢复时写 `db_recovered`。面试别说“断库时写了一条 db_down”。

`event()` 用 `try/except: pass` 包住：事件写失败不能影响数据面。这是对的取舍，但也意味着“事件表缺一条”不能当成“没发生”。

### 8.3 healthcheck：liveness 不是 readiness

两个 `/healthz`：

| 服务 | 字段 | 用途 |
|---|---|---|
| api `:8001/healthz` | `version / mqtt.connected / mqtt.frames / db.watermark / ws.clients / ws.timeouts / ws.accepted` | 页面头部、回滚轮询版本 |
| ingest `:8081/healthz` | `rows_written / pending_in_buffer / wal_pending_bytes / replay_thread_alive / replay_tick_age_s / wal_stuck / frame_age_s / lag_seconds / batches` | 判断采集是否健康 |

> 端口口径：容器里 `HEALTH_PORT=8081`（`code/ingest/Containerfile`）；本机直跑不设这个 env 时默认 **8091**（宿主 8081 被 Penpot 占，`code/ingest/README.md`）。面试别说“ingest 就是 8081”，会被问“宿主直跑呢”。

**重要区分**：

- compose 的 healthcheck 是 **liveness**：`urllib.urlopen(...)` 只要 HTTP 200 就算过，**不解析 body 的 `ok`**。
- api 的 `/healthz` 在 DB 挂时返回 `{"ok": false}`，但 HTTP 仍是 200；compose 仍判 healthy。
- ingest 的 `/healthz` 永远 200；DB 挂时它仍 healthy，这是**有意**的——它在用 WAL 兜数据，重启也没用；要看 `wal_pending_bytes` 判断病情。
- 所以“容器 healthy”≠“数据链路健康”。面试被问“怎么发现库挂了”，答：“看 api `/healthz` 的 `db.ok`、ingest 的 `wal_pending_bytes` 持续涨、`events` 里的恢复记录；compose 的 healthcheck 只保证进程活着。”

**看门狗与退出码**：

| 退出码 | 含义 | 首查 |
|---|---|---|
| 0 | 正常退出 | —— |
| 1 | 应用异常 | 日志 traceback |
| **3** | **replay 卡死，看门狗主动退出** | `wal_pending_bytes`、`replay_tick_age_s`；RB-03 表里漏了这条 |
| 137 | SIGKILL（常见 OOM） | `docker inspect --format '{{.State.OOMKilled}}'` |
| 143 | SIGTERM（`docker stop`） | 正常停栈；ingest 会先 flush |

### 8.4 诊断包：17 个 zip 条目 = 14 个文件 + 3 个目录

`deploy/scripts/diag.sh` 收集：

| 文件 | 内容 | 回答什么 |
|---|---|---|
| `system.txt` | 版本、时间、`compose ps`、容器状态、healthz | 现场什么版本、谁挂了 |
| `config/env.redacted` | 去掉密码行 | 配置有没有被改 |
| `config/compose.yaml` | 编排快照 | 服务/端口/资源 |
| `logs/{mqtt,db,ingest,api,web}.log` | 每容器 300 行 | 出错前后 |
| `mqtt-tail.ndjson` | 最近 100 条原始消息 | 数据到没到 Broker |

- `make diag` 在 `Makefile:81-82` 还是 `TODO(B 批)`，**直接跑只会打印 TODO**。真正能用的是 `bash deploy/scripts/diag.sh`（或 `make` 里补一行）。面试现场如果要演示，别按 README 敲 `make diag`。

- `mqtt-tail` 的端口用 `${MQTT_PORT:-1884}`，读的是**当前 shell 环境**，不是 `.env`；`.env` 改了端口而 shell 没导出，会抓错端口。

### 8.5 pg-perf：只读体检

```sql

select count(*) from telemetry where ts > now() - interval '5 minutes';
```

期望 `ChunkAppend` + 只列一个 chunk。若全表扫：时间条件不是常量/可折叠、对 `ts` 做了函数运算、或用了参数化查询让裁剪失效。

## 9. 部署与回滚

> 导图原句：
> - podman 构建 → docker load → compose 运行
> - 离线包 660MB（镜像 + 编排 + 脚本）
> - 回滚 12 秒（切 tag + 轮询版本）
> - 坏版本检测 48 秒（healthcheck 参数决定）
> - nginx 缓存旧 IP → 502，用 resolver 变量修
> - 镜像架构：当前 amd64，ARM 需重建

### 9.1 为什么构建用 Podman、运行用 Docker

ADR-0004 的来龙去脉：

1. 本机 Docker 的 buildx 在受限环境下写不了 `~/.docker/buildx`，构建直接失败；
2. 本机有 Podman 5.4.2，构建不需要 daemon，产物是标准 OCI 镜像；
3. 运行仍用 Docker Compose（`pull_policy: never` 用本地镜像）。

衔接：`podman save | docker load`。代价：

- 多一步导出导入，CI 要显式写；
- 两个运行时各占一份存储（`/var/lib/containers` 与 `/var/lib/docker`）；
- buildah 要 `--isolation=chroot --cgroup-manager=cgroupfs`（够不到宿主 systemd 的 cgroup），基础镜像要预置（`--pull=never`）。

**面试口径**：“构建与运行解耦，接口是 OCI 镜像。换运行时只换最后一步，不影响镜像内容。”

### 9.2 离线包：660MB 里有什么

`deploy/scripts/bundle.sh` 打 `dist/interroll-poc-<tag>.tar.gz`，本机实测 **660MB**。内容：

| 内容 | 说明 |
|---|---|
| `images.tar` | api / ingest / web + `eclipse-mosquitto:2` + `timescale/timescaledb:latest-pg17`，约 3GB 未压缩 |
| `deploy/compose/compose.yaml` + `mosquitto.conf` | 编排 |
| `deploy/db/init.sql` | 边缘库初始化 |
| `.env.example` | 环境模板 |
| `deploy/scripts/{load,rollback,diag}.sh` | 现场运维 |
| `runbook/RB-01、RB-02` | 部署/回滚手册 |

**不包含**：`forwarder`、`simulator`、`init-center.sql`。所以离线包只能起边缘五件套，不能演练中心侧/现场造数。

**load.sh 的关键**：podman 给本地镜像加 `localhost/` 前缀，load 后要 `docker tag localhost/interroll-poc-api:$TAG interroll-poc-api:$TAG` 摘掉，否则 compose 的 `image:` 名字对不上。`podman save` 不加 `-m` 会把后面的参数当成同一个镜像的 tags，打出“1 个镜像 5 个名字”的坏包——脚本里特意加了 `-m`。

### 9.3 回滚：12 秒，先校验再动手

`deploy/scripts/rollback.sh` 步骤：

1. 要求传 `TAG`，否则退出 2；
2. 校验 `interroll-poc-{api,ingest,web}:$TAG` 三个镜像都在本地，缺一个就退出 3（**不做半截回滚**）；
3. `sed -i` 改 `.env` 的 `APP_VERSION=$TAG`；
4. `compose up -d --no-build api ingest web`（只重建应用容器，不碰库）；
5. 轮询 `http://127.0.0.1:8001/healthz` 的 `"version"`，最多 30 次 ×1s；
6. 报版本 → 退出 0，打印耗时。

RB-02 实测：`0.3.1 → 0.3.0` **12 秒**。数据不动。

**边界**：

- 只校验/重建 api/ingest/web；**forwarder 和 simulator 不参与**。center profile 下回滚会版本不一致。
- 不碰数据库；“数据没动”指没丢数据，不是行数不变。
- `sed` 改 `.env`，如果文件里没有 `APP_VERSION=` 行，改不进去；`APP_VERSION=$TAG compose up` 仍对本次生效，但 `.env` 没持久化。
- 轮询的是 api 的版本；api 起来了不代表 ingest/web 都就绪（compose 的 healthcheck 会继续探）。

### 9.4 坏版本检测：48 秒这个数要小心

RB-02 的演练：

| 步骤 | 动作 | 实测 |
|---|---|---|
| 1 | 记录 `telemetry` 行数 | 9,027,607 |
| 2 | `APP_VERSION=0.3.2` → `compose up -d api` | 容器起来，`/healthz` 返回 **503** |
| 3 | 等 compose 判 `unhealthy` | **48 s**（`start_period 20s + interval 15s × retries 3`） |
| 4 | `rollback.sh 0.3.1` | **12 s** |
| 5 | 再记录行数 | 9,052,015（期间照常入库，未回退） |

**算术对不上**：`20 + 15×3 = 65s`，不是 48s。可能当时 healthcheck 参数不同，或 48s 是从别的观测点算的。**面试不要现场推导这个公式**；说“实测 48 秒，参数是 start_period 20s / interval 15s / retries 3，具体计时口径以 runbook 记录为准”最稳。如果被追问，就承认“公式和观测值有出入，我没复现”。

**端到端 60 秒 = 检测 48s + 回滚 12s。** “30 秒回滚”指的是“决定回滚之后”的 12 秒；如果要求端到端 30 秒，得把 healthcheck 调紧（`interval 10s / retries 2 / start_period 10s` ≈ 30s 检测），或部署脚本主动探活而不是等 compose。

### 9.5 nginx resolver 的 502（见 §1.2）

一句话：容器重建 IP 变，nginx 启动时只解析一次；`resolver 127.0.0.11 valid=10s` + 变量 upstream 强制重解析。这是部署篇最容易被追问的“你踩过什么坑”。

### 9.6 镜像与架构

本机实测（2026-11-22）：

| 镜像 | 大小 |
|---|---|
| `interroll-poc-api:0.3.1` | 310MB |

## 10. 技术栈选型

> 导图原句：
> - Python：边缘内存 25/44MB，吞吐有 100 倍余量
> - .NET AOT：交叉编译 1.32MB、启动 1.7ms
> - AOT 不支持 32 位 x86；EF Core 基本不可 AOT
> - 32 位老设备只能 Go/C
> - 产品化建议：团队 .NET 则用 ASP.NET Core + MQTTnet

### 10.1 Python 站得住吗

本机实测（`docker stats --no-stream`，2026-11-22）：

| 容器 | 内存 | 镜像 |
|---|---|---|
| ingest | **26.29MiB** | 224MB |
| api | **45.34MiB** | 310MB |

和 ADR-0006 的“25/44MB”几乎一致，可以直接引用。两个服务共约 **70MB**，4C/8G 边缘机毫无压力。

**吞吐口径**：

- 业务量 360 行/秒；
- 纯插入 benchmark 44,521 行/秒（约 124 倍）；
- 端到端 ingest 实测约 13,000 行/秒（约 36 倍）；
- 所以“100 倍余量”只在纯插入口径成立；**说“几十倍端到端余量”更稳**。

**为什么 Python 够**：这是 I/O 密集型（MQTT 收、DB 写），不是 CPU 密集；GIL 不影响“一个 paho 线程 + 一个主循环 + 一个回放线程”的模型。真要压满单进程，瓶颈会先出现在 `executemany`/commit，不是 Python 语法。

### 10.2 .NET NativeAOT 的三个数字

`code/dotnet-aot-probe/README.md`（x86_64 主机，.NET 10.0.15）：

| 产物 | 体积 | 验证 |
|---|---|---|
| `linux-arm64` AOT | **1,385,904 B ≈ 1.32MB** | `aarch64-linux-gnu-readelf -h` → ELF64 / AArch64 / PIE |
| `linux-x64` AOT | **1,341,016 B ≈ 1.28MB** | 本机直接跑 |
| 启动耗时（x64，20 次均值） | **≈1.7ms** | 容器内 `date +%s%N` 取差 |
| arm64 产物在 x64 跑 | `exec format error` | 证明是真交叉产物，不是模拟 |
| 交叉编译总耗时 | ≈4 分钟（SDK 缓存后） | 可进 CI |

**踩过的三个坑**（面试讲“能落地”的细节）：

1. `cannot find crtbeginS.o`：只装 binutils 不够，要 `gcc-aarch64-linux-gnu`；
2. `objcopy: Unable to recognise the format`：ILCompiler 调**裸名** `objcopy`，用了宿主 x86 版本；建 `/opt/arm64bin` 符号链接，只在该步前置 `PATH`；
3. `CS0103: Console 不存在`：没开 `ImplicitUsings`。

**没有 QEMU**：交叉编译产出真二进制，但本机没有 binfmt，跑不了 arm64；要验证“能运行”得在 ARM 机器或 CI 的 arm64 runner。

### 10.3 AOT 的边界

| 限制 | 说明 |
|---|---|
| 32 位 x86 | NativeAOT 不支持；Linux 32 位运行时也已停 |
| EF Core / Dapper | 反射重，基本不可 AOT；要么换手写 SQL + Npgsql，要么框架依赖发布 |
| `System.Text.Json` | 必须源生成（`JsonSerializerContext`） |
| Npgsql | 要核版本/裁剪配置 |
| 调试 | 没有 JIT，现场只能靠日志 + core dump；开发期建议先框架依赖发布 |
| 镜像基线 | Alpine 约 130MB；AOT 可到 15MB 级（带 ASP.NET Core 通常 10–15MB） |

**“1.32MB”是 Hello 级**，不是带 ASP.NET Core 的完整服务；面试要主动说“这是探针下限，真实服务 10–15MB 量级”。

### 10.4 32 位老设备怎么办

- .NET NativeAOT 不支持 32 位 x86；
- Python 在 32 位 Linux 上也越来越难（发行版/轮子）；
- 只能 Go（`GOARCH=386`）或 C。
- 这不是本项目的目标场景（ADR-0006 明确“不为 32 位 x86 做兼容”），但面试官如果问“老工控机怎么办”，要能答“换 Go/C，不要在 .NET/Python 上硬扛”。

### 10.5 产品化建议

| 场景 | 选择 | 理由 |
|---|---|---|
| PoC / 48 小时闭环 | Python（现状） | I/O 密集、交付快、内存 70MB |
| 产品化、团队 .NET | ASP.NET Core + MQTTnet + Npgsql | 团队栈、AOT/交叉发布、边缘机扛得住 |
| ARM64 交付 | 两者都可；.NET 可直接 `dotnet publish -r linux-arm64 -p:PublishAot=true` | 1.32MB 探针证明可行 |
| 32 位 x86 | Go / C | 两边都不合适 |

**迁移成本**：MQTT 协议无关，ingest/api 重写不改变架构（批量、幂等、spool/WAL、健康检查）；真正要重写的是“状态机 + SQL”，不是“架构”。

### 10.6 这一节的讲法（35 秒）

> “PoC 用 Python 是 I/O 密集 + 交付速度的取舍：实测 ingest 26MB、api 45MB，两个服务 70MB；360 行/秒，端到端有几十倍余量。产品化如果按团队栈走 .NET，我在 x64 上交叉编译过 ARM64 的 NativeAOT：1.32MB、启动 1.7ms，说明边缘机扛得住；但这是 Hello 级，带 ASP.NET Core 通常 10–15MB。代价是 EF Core 这类反射重的库不能用，JSON 要走源生成，调试没有 JIT。32 位 x86 老机器两边都不合适，该换 Go。迁移不会改架构，批量、幂等、WAL、健康检查都能原样搬。”

### 11.1 先讲边界，再讲功能

面试官最容易记住的不是“你做了个看板”，而是“你知道哪里会丢、谁兜底、RPO 多少”。建议开场 30 秒：

### 11.2 七个量化结论（带口径）

| # | 结论 | 数字 | 怎么测 | 口径/警告 |

| 1 | 断流不丢不重 | 0 丢 / 0 重 | 停 Broker 60s，闭合窗口逐条比对 `(zone,drive,ts,seq)` | 单线、S 档；稳态跨机另有 0.2% 问题（§12.1） |

### 11.3 三分钟版本

## 12. 复核发现与风险清单

> 这一节是本次（2026-11-22）对当前运行栈和仓库的复核结果。
> 不是“项目做得不好”，而是**面试前必须知道的口径**：哪些能说、哪些要加限定、哪些现场别碰。

### 12.1 【重要】forwarder 稳态漏行约 0.2%：水位用 ts 做游标的固有缺陷

> **D 级**：本节是本次复核（2026-11-22）对当前运行栈的只读查询结果，与“跨机 0 丢”的既有结论形成边界冲突；不是 MQTT/ingest 的问题。

#### 证据（只读查询，当前运行栈）

固定闭合窗口，边缘库 vs 中心库逐条比对：

| 窗口（UTC） | 边缘 | 中心 | 缺失 | 缺失率 |
|---|---|---|---|---|
| 00:15–00:30（15 min） | 324,000 | 323,270 | **730** | 0.225% |
| 00:05–00:10（5 min） | 108,000 | 107,768 | **232** | 0.215% |
| 00:20–00:21（1 min） | 21,600 | 21,578 | **22** | 0.102% |
| 23:30–23:45（15 min） | 324,000 | 323,106 | **894** | 0.276% |
| 22:00–22:15（15 min） | 324,000 | 323,075 | **925** | 0.285% |

边缘库每个 15 分钟窗口都精确 **324,000 = 360 × 900**，说明模拟器/ingest 没有丢；缺失全部发生在**边缘→中心**。重复为 0（`count(*) = count(distinct 主键)`），说明 `ON CONFLICT` 正常。

**缺失行的形态**：不是分散的，而是**聚在单个 ts**。例如 `00:20:55.617`：

| 库 | 该 ts 行数 | seq 范围 |
|---|---|---|
| 边缘 | **36** | 12674665–12674700 |
| 中心 | **16** | 12674665–12674680（缺 12674681–12674700） |

中心保留了该 ts 的**前 16 行**，缺后 20 行；下一个 ts 的行是完整的。5 分钟窗口里 11 个缺失事件，每个事件缺 3–35 行，全部是单 ts。

#### 机制（高置信推断，与代码一致）

`code/forwarder/main.py`：

```sql
-- 只按 ts 推进
select ... from telemetry where ts > %s order by ts limit 500;
...
watermark = rows[-1][0]     # 最后一个 ts
```

ingest 的 flush 是 **200 行/批**，一拍是 **36 行**；200 不是 36 的整数倍，flush 边界经常切在一拍中间：

1. ingest 第一批提交了 `00:20:55.617` 的 16 行；
2. forwarder 正好在此时读到这一拍，`watermark = 00:20:55.617`；
3. ingest 第二批提交剩下的 20 行（同 ts）；
4. forwarder 下一轮 `ts > 00:20:55.617`，这 20 行永远读不到；
5. 120s 重叠回扫本可补，但它的触发条件是**空闲 30 秒**：

```python
if not rows:
    if gap_from is None and time.monotonic() - last_idle > 30:
        gap_from, gap_to = watermark - timedelta(seconds=120), watermark
        last_idle = time.monotonic()
```

而 `last_idle` 在**每次成功 push 后都会重置**（`:120`），所以连续流量下永远不会“空闲 30 秒”，回扫不跑。

还有第二层叠加：forwarder 的 `ORDER BY ts LIMIT 500` 里，500 也不是 36 的整数倍，读批本身就会切在某一拍中间。即使 ingest 整拍提交，`LIMIT 500` 仍可能只读到某一拍的前 32 行，剩下 4 行被 `ts >` 跳过。**两个“切拍”叠加，所以缺的行数在 3–35 之间变化，不是固定 4 行。**

**为什么 60 秒演练是 0 丢**：停中心期间 `push` 一直失败，`watermark` **不前进**；恢复后正常扫描从旧水位重新读，断链窗口里的行（`ts > 旧水位`）会被重新推一遍，重复由 `ON CONFLICT` 挡掉。**这不是 120s 回扫的功劳**——回扫只在启动或“边缘 30 秒没有新行”时才触发，连续流量下不跑。演练窗口的 0 丢是真的，但它不代表稳态：同一 ts 被拆成两批的迟到行，仍然不在“`ts > 旧水位`”的覆盖范围内。

#### 影响

- 中心库少约 **0.2–0.3%** 的行；对“看趋势/做聚合”影响很小，对“逐条对账/计件”不能接受。
- 这是**设计层**问题，不是 MQTT/ingest 丢：边缘库完整、中心无重复。
- 根因一句话：**`ts` 不是唯一的行标识；同一 ts 的行会分多批提交，任何一次读到部分就把整批同 ts 判成已读。**

#### 修法（从轻到重）

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 周期性短回扫 | 每 10–30s 重扫最近 5s，`last_scan` 独立于 `last_idle`；`ON CONFLICT` 去重 | 读放大：每 10s 扫 5s = 50%，每 30s 扫 5s = 17%；能补同 ts 漏行，窗口内最终一致 |
| B. 边缘行号游标（推荐） | 边缘 `telemetry` 加 `id bigserial`，forwarder `where id > last_id order by id limit 500`；中心存 `edge_id` | 改 schema；但游标单调、无 ts 歧义；`nextval` 在冲突时消耗号但不落库，序号可跳，不影响 |
| C. 每设备 `(ts, seq)` 游标 | 36 台设备各自水位，`(ts,seq) > (wm_ts,wm_seq)` | 精确，但代码复杂；seq 在真实设备上每台独立，不能拿全局 seq 排序 |
| D. 只在边缘聚合后回传 | 中心只收 1m 桶，天然没有“同 ts 多行” | 符合 ADR-0002 原意，但改变产品语义 |

**最小改动是 A**：把 `last_idle` 换成 `last_gap_scan`，每 30s 无条件开一次 5s 回扫。**产品化建议 B**：用边缘行号做游标，彻底摆脱 ts 歧义。

#### 面试怎么讲（建议逐字）

> “跨机这块我做过 60 秒断链演练，恢复后 1 秒追平，窗口 25,668 条 0 丢 0 重。但我后来用闭合窗口复核稳态，发现中心比边缘少约 0.2% 的行。查下来不是 MQTT 或 ingest 丢——边缘每个 15 分钟窗口都精确 324,000 行；缺的行全部聚在单个 ts，中心保留了该 ts 的前若干行、缺后面的连续 seq。根因是 forwarder 用 `max(ts)` 做水位：ingest 200 行一批，一拍 36 行，flush 边界会把同一 ts 切成两批；forwarder 读到第一批就把水位推过这个 ts，第二批永远读不到。120 秒重叠回扫本来能补，但它只在启动或边缘空闲 30 秒后触发，连续流量下不跑；60 秒演练之所以 0 丢，是因为停中心期间水位没动，恢复后从旧水位重读把窗口盖住了，不是回扫的功劳。修法最轻是每 30 秒无条件回扫最近 5 秒；产品化是给边缘行加 `bigserial`，用行号做游标。这个 bug 让我更清楚：**‘0 丢’必须带窗口、闭合、比对键三个口径，否则数字会骗人。**”

## 13. 必答 15 题（速查）

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 为什么边缘 5 个容器？ | 采集/存储/接口/展示各自独立，看板挂了不影响落库；一台工控机不需要 K8s。 |
| 2 | QoS1 和 QoS2 差在哪？ | QoS2 四段握手、会话内不重复；断线在途仍可能丢，端到端靠幂等。 |
| 3 | 为什么主键带 zone 和 seq？ | 六区都有 D01–D06，只 drive 会撞；seq 是设备自增，用来区分同 ts。 |
| 4 | WAL 怎么做到 kill -9 不丢？ | 每条先写 WAL，flush 时 fsync；崩溃后从 `wal.commit` 回放，重复由主键挡。 |
| 5 | 断电为什么不保证？ | fsync 在 flush 时做，最后 ≤1s 的 write 可能还在 page cache。 |
| 6 | 为什么批量 200 行/1s？ | 360/s 下 200 行约 0.56s 攒满；1s 是低流量兜底；commit 约 1.8/s。 |
| 7 | hypertable 一定更快吗？ | 小数据量不一定（2M 行 8.4 vs 11.3ms，普通表更快）；价值在 drop/压缩/索引规模。 |
| 8 | 压缩为什么没收益？ | 压缩和保留都 7 天，chunk 刚可压缩就可删除；线上 0 压缩 chunk。 |
| 9 | 长窗口为什么快？ | 查 1 分钟连续聚合，1h 只有 60 点；LTTB 只在 24h 1440→1000 用。 |
| 10 | 前端怎么扛 2000 点/秒？ | 服务端 10fps 快照 + 前端 90ms 丢帧 + 120 点缓冲；抗的是渲染速率。 |
| 11 | WS 客户端读不动怎么办？ | send 2s 超时 → close(1013)；每客户端一个协程，不拖死服务端。 |
| 12 | 重连风暴怎么控？ | 指数退避 + 抖动；峰值换时长；jitter 0/3/10 → 664/248/44。 |
| 13 | 跨机为什么不用 bridge？ | WAN 断几小时 broker 队列扛不住；落地库 + 水位重放才不丢。 |
| 14 | 回滚为什么 12 秒？ | 只切 tag、只重建 api/ingest/web、不碰库；先校验镜像，轮询 healthz 版本。 |
| 15 | Python 还是 .NET？ | PoC Python（I/O 密集、70MB）；产品化团队 .NET 用 ASP.NET Core + MQTTnet；AOT 1.32MB 探针证明可行；32 位换 Go。 |
