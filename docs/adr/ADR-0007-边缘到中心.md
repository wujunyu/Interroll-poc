# ADR-0007 边缘到中心的推送方式

- **状态**：已接受
- **日期**：2026-11-21
- **相关**：P10、`code/forwarder/`

## 背景

边缘机已经有「设备 → broker → ingest → 本地库」的闭环。中心侧要拿数据，有两种做法：

| 方案 | 机制 |
|---|---|
| A. MQTT bridge | 边缘 mosquitto 配 `bridge` 连中心 broker，QoS1 跨桥转发 |
| B. 应用层 store-and-forward | 边缘库落地，转发进程按水位把数据推给中心 |

## 决策

**选 B（应用层转发）**，边缘库是唯一事实源，中心是汇聚副本。

## 理由

| 维度 | A. bridge | B. 应用层转发 |
|---|---|---|
| 断链 6 小时 | 只能靠 broker 队列（`max_queued_messages`，默认几千条就丢）| 边缘库落盘，**断多久都不丢** |
| 重放/补偿 | 难（要重放 broker 日志） | 天然（改水位即可） |
| 只传聚合值 | 难 | 易（转发时可只发 1m 聚合） |
| 幂等 | 依赖 broker | 靠主键 `(site_id, zone_id, drive_id, ts, seq)` |
| 复杂度 | 低 | 中（多一个进程） |

工业现场的 WAN 断几小时是常态，**broker 队列扛不住，只有落地才可靠**。

## 代价

- 多一个常驻进程与一套水位逻辑；
- 首次启动要决定回放窗口（`START_WINDOW`，默认 600s），否则会把历史全量拉到中心；
- 水位推进必须处理「迟到行」：`ts > 水位` 会漏掉后到但时间戳更早的点，
  所以加了**重叠回扫**（每 30s 重扫最近 `OVERLAP=120s`，重复由 `ON CONFLICT` 挡掉）。

## 实测

| 项 | 结果 |
|---|---|
| 中心停止 60 秒 | 转发进程报错重试，水位不动 |
| 恢复后追平 | **1 秒** |
| 窗口 25,668 条 | 边缘 25,668 / 中心 25,668 / 重复 0 / 缺失 0 |
| 迟到行缺陷 | 修复前窗口少 184 条，重叠回扫后为 0 |

## 面试口径

> "边缘到中心不用 MQTT bridge，用应用层转发：边缘库落地、按水位推、幂等去重。
> 因为 bridge 只能靠 broker 队列扛断链，断几小时就丢；落地库可以断多久都不丢。
> 坑在水位：`ts > 水位` 会漏迟到行，我们实测一个窗口少了 184 条，
> 后来加了 120 秒重叠回扫才补齐。"
